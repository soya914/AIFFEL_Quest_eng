# Chapter 7. 현대적 ML 엔지니어를 위한 개발 환경

### 7-1. VS Code 원격 개발이 ML 엔지니어에게 왜 필수적인가 (GPU 서버 활용 관점)

**핵심은 "코드를 데이터가 있는 곳으로 보내는 것"입니다.**

ML 작업의 무게중심은 GPU 서버에 있습니다. 학습 데이터가 수백 GB이고 GPU도 거기 있으니, 코드만 로컬에서 짜고 실행은 원격에서 하는 구조가 됩니다. 문제는 그 사이의 개발 경험입니다.

**단순 SSH + vim의 한계**: 자동완성, 타입 힌트, 정의로 이동, 디버거 중단점 같은 IDE 기능을 쓸 수 없습니다. 텐서 shape 오류처럼 ML에서 가장 흔한 버그가 실행 전에 안 잡힙니다.

**로컬에서 짜고 rsync/git push로 옮기는 방식의 한계**: 매번 동기화 지연이 생기고, 로컬과 원격의 환경 차이(CUDA 버전 등) 때문에 "로컬에선 되는데 서버에선 안 되는" 문제가 반복됩니다.

**VS Code Remote의 해법**: 원격 서버에 VS Code Server 에이전트를 설치해 **코드 분석·인덱싱·디버깅 프로세스는 서버에서 실행하고 UI 렌더링만 로컬로 가져옵니다.** 파일이 서버에 있으니 동기화가 없고, 언어 서버가 서버의 파이썬 환경을 직접 보므로 실제 실행 환경과 자동완성이 일치합니다. 디버거 중단점을 걸면 GPU 위의 텐서를 그 자리에서 들여다볼 수 있습니다.

**제 프로젝트에서는 규제 측면의 이유가 하나 더 있습니다.** 학습 데이터가 게시글 본문이라 연락처·계좌번호 같은 개인정보를 포함합니다. 원격 개발은 **데이터를 로컬로 내려받지 않고도 작업이 가능**하게 만들어, 개인정보를 서버 경계 밖으로 내보내지 않는다는 통제를 기술적으로 강제합니다. 편의 기능이 아니라 규정 준수 수단이 되는 셈입니다.

### 7-2. 주피터의 세 가지 문제를 "하이브리드 솔루션"이 각각 어떻게 해결하는가

하이브리드 솔루션의 구조는 **"탐색·시각화는 노트북에서, 핵심 로직은 `.py` 모듈에서"** + `%autoreload 2`입니다. 세 문제가 각각 이렇게 풀립니다.

**문제 1 — 실행 순서의 혼란**

원인은 노트북 셀에 **상태(state)와 정의(definition)가 뒤섞여 있다**는 것입니다. 셀 3에서 정의한 함수를 셀 1이 수정하면, 커널 메모리에는 낡은 정의가 남습니다.

해법: 정의를 전부 `.py` 모듈로 옮깁니다. 모듈은 `import` 시점에 **항상 파일 처음부터 끝까지 순서대로** 실행되므로 실행 순서가 결정적입니다. 노트북에는 상태만 남고, 그 상태는 언제든 재실행으로 복원됩니다. `autoreload`가 파일 저장 시 모듈을 다시 읽어주므로 커널 재시작 없이도 낡은 정의가 남지 않습니다.

**문제 2 — 리팩토링의 어려움**

원인은 노트북이 IDE의 정적 분석 대상이 아니라는 점입니다.

해법: 코드가 `.py`에 있으면 Rename Symbol, Go to Definition, Find All References가 전부 작동합니다. 노트북에는 `from my_project.model import LitClassifier` 같은 import 한 줄만 남으므로, 이름을 바꿔도 고칠 곳이 한 곳입니다.

**문제 3 — 버전 관리와 테스트**

원인은 `.ipynb`가 코드와 **실행 결과(출력, base64 이미지)를 같은 JSON에 담는다**는 것입니다. 실제로 이번 강의 노트북도 마크다운만 있는데 파일 크기가 21MB입니다 — 전부 삽입 이미지입니다. 이런 파일은 Git diff가 읽히지 않습니다.

해법: 핵심 로직이 `.py`에 있으면 diff가 코드 변경만 보여줍니다. `pytest`로 단위 테스트를 붙일 수 있고, CI에서 자동 실행됩니다. 노트북은 결과가 커밋돼도 상관없는 탐색용 산출물로 성격이 명확해집니다.

**정리하면 하이브리드는 타협이 아닙니다.** 노트북의 강점(즉각적 피드백)과 IDE의 강점(정적 분석·테스트)이 서로 다른 대상에 적용되므로, 둘 다 온전히 얻습니다.

### 7-3. "결정적 빌드"가 보장되지 않았을 때 팀 협업에서 발생하는 문제

**직전 과정에서 실제로 겪은 사례가 있습니다.**

붓꽃 분류 모델을 로컬에서 학습해 `model.joblib`으로 저장하고, Docker 이미지 안에서 그 파일을 불러오는 구조를 만들었습니다. 그런데 강의 자료의 Dockerfile은 이렇게 되어 있었습니다.

```dockerfile
RUN pip install --no-cache-dir fastapi uvicorn scikit-learn joblib python-multipart
```

**버전이 하나도 고정되어 있지 않습니다.** 제 로컬 학습 환경은 scikit-learn 1.9.0이었는데, 컨테이너는 빌드하는 시점의 최신 버전을 받습니다. joblib으로 직렬화된 모델은 내부적으로 클래스 구조에 의존하므로, 버전이 어긋나면 로드 시 경고가 뜨거나 최악의 경우 예측 결과가 달라집니다.

그래서 `requirements.txt`로 분리하고 `scikit-learn==1.9.0`으로 고정했습니다.

**여기서 드러나는 문제의 구조:**

**증상이 늦게, 엉뚱한 곳에서 나타납니다.** 빌드는 성공하고 컨테이너도 뜹니다. 문제는 예측 결과가 미묘하게 달라지는 형태로 나타나므로, 원인이 환경이라는 것을 의심하기까지 오래 걸립니다.

**"내 컴퓨터에선 되는데요"의 정체입니다.** 팀원 A가 오늘 빌드한 이미지와 팀원 B가 다음 주에 빌드한 이미지가 다른 라이브러리 버전을 담습니다. 같은 커밋, 같은 Dockerfile인데 결과가 다릅니다.

**실험 결과를 신뢰할 수 없게 됩니다.** ML에서는 이게 특히 치명적입니다. 모델 A와 B의 성능 차이가 아키텍처 때문인지 라이브러리 버전 때문인지 구분할 수 없으면, 그 실험은 의사결정에 쓸 수 없습니다.

**롤백이 무의미해집니다.** 성능이 떨어져서 지난주 커밋으로 되돌려도, 다시 빌드하는 순간 라이브러리는 최신 버전을 받습니다. 코드는 롤백됐지만 환경은 롤백되지 않았습니다.

### 7-4. `requirements.in`과 `requirements.txt`의 역할 차이

| | `requirements.in` | `requirements.txt` |
|---|---|---|
| 누가 쓰는가 | **사람이 직접** 작성·수정 | `pip-compile`·`uv lock`이 **자동 생성** |
| 무엇이 들어가는가 | 내가 **직접 쓰는** 라이브러리만 | 하위 의존성까지 **전체 트리** |
| 버전 표기 | 최소한의 제약 (`torch>=2.0`) | 정확히 하나로 고정 (`torch==2.5.1`), 해시 포함 가능 |
| 성격 | **의도(intent)** — 무엇이 필요한가 | **잠금(lock)** — 실제로 무엇이 설치되는가 |

**둘 다 Git에 커밋합니다.** `.in`은 의도를 남기고 `.txt`는 재현을 보장합니다. 하나만 있으면 안 됩니다.

- `.in`만 있으면 → 재현이 안 됩니다 (7-3의 문제)
- `.txt`만 있으면 → 200줄짜리 고정 목록 중 **어느 것이 내가 원해서 넣은 것이고 어느 것이 딸려 온 것인지 구분할 수 없습니다.** 라이브러리를 하나 빼고 싶을 때 무엇을 지워야 하는지 알 수 없습니다.

**철칙은 `.txt`를 손으로 고치지 않는 것입니다.** 버전을 바꾸고 싶으면 `.in`을 수정하고 다시 컴파일합니다. 손으로 고치면 의존성 간 호환성 해결(resolution) 결과가 깨져서, 도구가 보장하던 "이 조합은 서로 충돌하지 않는다"는 성질을 잃습니다.

**제 사례에 비춰보면**, 직전 과정에서 만든 `requirements.txt`는 사실 `.in`의 성격입니다. 직접 쓰는 5개만 적혀 있고 `numpy`, `scipy` 같은 하위 의존성은 고정되어 있지 않습니다. 프로젝트 규모가 커지면 `.in`/`.txt`를 제대로 분리해야 합니다.

# Chapter 8. PyTorch 생태계 심화

### 8-1. Lightning 전환 시 사라지는 코드 5가지

강의 자료의 Before/After 비교표(8.2)가 **6가지 항목**을 제시합니다. 그중 다섯을 골라 정리합니다.

| # | 항목 | 전통 PyTorch **[강의 표]** | Lightning **[강의 표]** |
|---|---|---|---|
| 1 | GPU 전송 | `.to("cuda")` 매번 호출 | `Trainer`가 자동 처리 |
| 2 | 학습/검증 분리 | 하나의 루프에 뒤섞임 | `training_step` / `validation_step`으로 명확 분리 |
| 3 | 메트릭 로깅 | `print()` 또는 수동 집계 | `self.log()` 한 줄 → TensorBoard/W&B 자동 연동 |
| 4 | 하이퍼파라미터 | 변수로 흩어져 있음 | `save_hyperparameters()` → 자동 저장·복원 |
| 5 | GPU 4대 확장 | 코드 재작성 필요 | `Trainer(devices=4)` 파라미터 한 줄 |
| (6) | 체크포인팅 | 직접 구현 | `ModelCheckpoint` 콜백 연결 |

**각 항목이 실제로 무엇을 없애는지**

**1. GPU 전송** — 모델과 배치마다 직접 옮겨야 하고, CPU/GPU를 오가려면 모든 호출 지점을 수정해야 합니다. `training_step`은 배치를 그냥 받습니다.

**2. 학습/검증 분리** — 8.2의 Before 코드를 보면 검증 루프가 학습 루프 안에 들어가 있고 `model.eval()`, `torch.no_grad()`, 정확도 집계가 뒤섞여 있습니다. Lightning은 이를 두 메서드로 나누고 **모드 전환(`train()`/`eval()`/`no_grad()`)도 자동 처리**합니다. 검증에서 `model.eval()`을 빠뜨리는 흔한 버그가 구조적으로 사라집니다.

**3. 메트릭 로깅** — `val_loss_sum += loss.item()` 후 배치 수로 나누던 코드가 `self.log(..., on_epoch=True)` 한 줄이 됩니다. 분산 학습에서는 GPU 간 집계까지 처리하는데, 직접 구현하면 상당히 까다로운 부분입니다.

**4. 하이퍼파라미터** — 이건 표를 보기 전에는 제가 떠올리지 못했던 항목입니다. `save_hyperparameters()`는 단순한 편의가 아니라 **체크포인트에 하이퍼파라미터를 함께 저장**하므로, `load_from_checkpoint()`만으로 모델 구조가 복원됩니다. Ch12의 재현성 논의와 직접 이어집니다.

**5. GPU 4대 확장** — `torch.distributed.init_process_group`, `DistributedSampler` 설정, rank별 분기가 `strategy="ddp"` 한 줄로 대체됩니다. 줄 수로는 이게 가장 큰 절감입니다.

**표에 없지만 함께 사라지는 것** — 역전파 3종 세트(`zero_grad()` / `backward()` / `step()`)입니다. `training_step`이 loss를 반환하면 Trainer가 순서대로 호출하므로, `zero_grad()`를 빠뜨려 그래디언트가 누적되는 고전적 버그가 불가능해집니다.

### 8-2. `setup`과 `train_dataloader`의 역할 차이 / 왜 분리하는가

| | `setup(stage)` | `train_dataloader()` |
|---|---|---|
| 하는 일 | 데이터 로딩·전처리·train/val/test **분할** | 분할된 데이터셋을 감싸는 **DataLoader 객체 생성** |
| 호출 시점 | `fit`/`test` 진입 시 stage별로 한 번 | 매 에포크마다 다시 호출될 수 있음 |
| 산출물 | `self.train_dataset` 등 **상태** | 매번 새로 만들어지는 **객체** |
| 분산 환경 | 모든 GPU 프로세스에서 호출 | 프로세스별로 호출되며 Lightning이 sampler를 주입 |

**분리가 중요한 이유는 세 가지입니다.**

**① 비용의 성격이 다릅니다.** 데이터 분할은 무겁고 한 번만 하면 되는 작업입니다. DataLoader 생성은 가볍고 반복적입니다. 같은 함수에 두면 에포크마다 데이터를 다시 분할하게 되고, 더 나쁘게는 **분할 결과가 매번 달라져 검증셋에 학습 데이터가 섞일 수 있습니다.**

**② 분산 학습에서 프레임워크가 개입할 지점이 필요합니다.** DDP에서는 각 GPU가 데이터의 서로 다른 부분을 봐야 하므로 `DistributedSampler`가 필요합니다. Lightning이 이걸 자동 주입하려면 **DataLoader가 만들어지는 시점을 프레임워크가 제어**해야 합니다. 미리 만들어진 DataLoader를 넘겨받으면 개입할 수 없습니다.

**③ 같은 분할에 다른 로딩 설정을 적용할 수 있습니다.** batch_size나 num_workers만 바꿔 실험할 때 데이터를 다시 읽을 필요가 없습니다.

**덧붙여 `prepare_data`와의 구분도 중요합니다.** 다운로드처럼 **한 번만** 실행되어야 하는 작업은 `prepare_data`에 넣습니다. 이건 rank 0에서만 호출되기 때문입니다. `setup`은 모든 프로세스에서 호출되므로 여기에 다운로드를 넣으면 GPU 개수만큼 동시에 같은 파일을 쓰려 해서 충돌합니다.

### 8-3. `_shared_step` 패턴을 내 프로젝트에 적용하면

**공통 로직 (`_shared_step`)**

```python
def _shared_step(self, batch):
    input_ids, attention_mask, y = batch
    logits = self(input_ids, attention_mask)
    loss = self.loss_fn(logits, y)          # class weight 적용된 BCE/CE
    probs = torch.softmax(logits, dim=1)[:, 1]   # 사기일 확률
    return loss, probs, y
```

배치 언팩 → forward → loss 계산 → **위험도 확률 산출**까지가 세 단계 공통입니다. 확률까지 공통으로 뽑는 게 핵심인데, 제 프로젝트의 실질 지표가 정확도가 아니라 **순위 기반(일별 Recall@2000)**이라 어느 단계에서든 확률이 필요하기 때문입니다. 다만 순위를 매기려면 **각 샘플이 어느 날짜의 게시글인지**도 함께 흘려보내야 하므로, 배치에 `created_date`를 포함시킵니다.

**단계별로 달라지는 부분**

| 단계 | 달라지는 것 |
|---|---|
| `training_step` | loss만 반환. 스텝 단위 로깅. 클래스 불균형이 심하므로 **가중 샘플링된 배치**를 받음 |
| `validation_step` | 확률·정답·**날짜**를 누적만 함. 배치 단위로는 순위를 매길 수 없으므로 집계는 에포크 종료 훅에서 |
| `test_step` | 시간 기준으로 분리한 **최근 30일 데이터**에서만 평가. 카테고리별·신규가입자 여부별 **슬라이스 지표**를 함께 산출 |

**에포크 종료 시점의 집계 로직**

```python
def on_validation_epoch_end(self):
    # 검증 기간 전체에서 상위 2,000건이 아니라, 날짜마다 상위 2,000건
    recalls = []
    for day in self.val_dates.unique():
        m = self.val_dates == day
        probs, labels = self.val_probs[m], self.val_labels[m]
        k = min(2000, len(probs))
        topk = probs.topk(k).indices
        n_fraud = labels.sum()
        if n_fraud > 0:
            recalls.append(labels[topk].sum() / n_fraud)
    self.log("val_recall_at_2000", torch.stack(recalls).mean(), prog_bar=True)
```

**여기서 드러나는 함정 두 가지**

첫째, `_shared_step`은 배치 단위 계산에만 적합합니다. Recall@K처럼 전체 순위가 필요한 지표는 배치 안에서 계산할 수 없으므로, 집계는 에포크 종료 훅으로 빼야 합니다.

둘째가 더 중요한데, **검증 기간 전체에서 상위 2,000건을 뽑으면 지표의 의미가 달라집니다.** 검증셋이 한 달치라면 그건 "한 달 동안 2,000건을 검토하는 시스템"의 성능이 됩니다. 실제 운영은 **하루 2,000건**이므로, 반드시 **날짜별로 상위 2,000건을 뽑아 Recall을 구하고 그 평균**을 내야 운영 조건과 일치합니다. 지표 이름은 같은데 값이 크게 달라지는 지점입니다.

### 8-4. `overfit_batches=1` 실패 시 의심할 원인 3가지와 디버깅 방법

`overfit_batches=1`은 단 하나의 배치를 반복 학습시켜 loss가 0에 수렴하는지 보는 테스트입니다. 데이터 1개도 암기 못 하는 모델은 일반화를 논할 단계가 아닙니다. **모델의 표현력 문제가 아니라 파이프라인 버그를 잡는 도구**입니다.

**원인 1 — 그래디언트가 흐르지 않음**

가중치가 아예 업데이트되지 않는 경우입니다. 옵티마이저에 파라미터가 등록되지 않았거나, 중간에 `.detach()`나 `.item()`으로 그래프가 끊겼거나, `requires_grad=False`가 걸려 있거나, in-place 연산이 그래프를 망가뜨린 경우입니다.

> **디버깅**: `loss.backward()` 직후 `[p.grad for p in model.parameters()]`를 확인합니다. `None`이거나 전부 0이면 확정입니다. 더 간단하게는 학습 전후 가중치 텐서를 저장해 `torch.equal`로 비교합니다 — 같으면 업데이트가 안 된 것입니다.

**원인 2 — 데이터와 레이블의 정렬이 깨짐**

셔플 과정에서 x와 y의 대응이 무너지면, 모델은 무작위 레이블을 학습하려 듭니다. 배치 1개라면 암기가 가능해야 하는데도 수렴이 느리거나 불안정합니다.

> **디버깅**: 배치 하나를 꺼내 **직접 눈으로 확인**합니다. 제 프로젝트라면 게시글 텍스트를 디코딩해서 출력하고 레이블과 대조합니다. 자동화된 검사보다 이게 확실합니다. `Dataset.__getitem__`이 인덱스를 제대로 쓰는지도 함께 봅니다.

**원인 3 — 수치적 불안정 (NaN/Inf)**

학습률이 지나치게 크거나, `log(0)`이 발생하거나, 입력이 정규화되지 않아 초기 loss가 폭발하는 경우입니다. NaN이 한 번 나오면 이후 모든 계산이 오염됩니다.

> **디버깅**: `torch.autograd.set_detect_anomaly(True)`로 NaN이 처음 생기는 연산을 특정합니다. 학습률을 1/10로 낮춰 증상이 사라지면 lr 문제입니다. `Trainer(gradient_clip_val=1.0)`으로 완화되는지도 확인합니다.

**추가로 흔한 것 — 손실 함수와 출력 형태의 불일치**

`nn.CrossEntropyLoss`는 내부에 log-softmax가 포함되어 있는데 모델이 이미 softmax를 적용한 값을 넘기는 경우입니다. 학습이 되긴 하지만 극도로 느립니다. 오류가 안 나서 발견이 늦습니다.

> **디버깅**: 초기 loss가 이론값과 맞는지 봅니다. 균형 잡힌 2-클래스면 `ln(2) ≈ 0.693`, 10-클래스면 `ln(10) ≈ 2.303`이어야 합니다. 이 값에서 크게 벗어나면 출력이나 손실 함수 쪽을 의심합니다.

# Chapter 9. GPU 하드웨어와 클라우드 인프라의 경제학

### 9-1. 3대 지표 중 분산 학습에서 가장 중요한 것 / "고속도로와 톨게이트" 비유

**답: 인터커넥트(Interconnect)입니다.**

**비유의 확장**

강의는 단일 GPU 안에서 메모리 대역폭을 설명하며 "고속도로가 아무리 넓어도 톨게이트가 좁으면 정체된다"고 했습니다. 분산 학습으로 넘어가면 **톨게이트가 하나 더 생깁니다.**

- **연산 속도(Tensor Core)** = 목적지 도시의 처리 능력
- **메모리 대역폭** = 도시 안으로 들어가는 톨게이트
- **인터커넥트** = **도시와 도시를 잇는 다리**

GPU를 4개로 늘리는 것은 도시를 4개로 늘리는 일입니다. 그런데 DDP에서는 매 스텝마다 모든 GPU가 그래디언트를 서로 교환해 평균을 냅니다(All-Reduce). 즉 **도시를 늘릴 때마다 도시 간 왕래량이 함께 늘어납니다.** 다리가 좁으면 도시를 아무리 늘려도 전체 처리량은 다리에서 막힙니다.

**왜 이것이 분산 학습에서 특히 결정적인가**

메모리 대역폭 부족은 각 GPU가 개별적으로 겪는 문제라, 손해가 GPU 수에 **비례**합니다. 반면 인터커넥트 병목은 **동기화 지점**에서 발생합니다. All-Reduce는 모든 GPU가 끝나야 다음 스텝으로 갈 수 있으므로, **가장 느린 통신 하나가 전체를 붙잡습니다.** 손해가 비례가 아니라 전체 정지로 나타납니다.

**실제 수치**: 강의에 나온 대로, NVLink가 있으면 GPU 수에 거의 비례하는 성능 향상을 기대할 수 있지만, NVLink가 없어 PCIe를 거치는 소비자용 RTX 카드는 **4장을 써도 3배 정도**에 그치는 경우가 많습니다.

강의의 GPU 가이드 표도 이 점을 명시합니다 — RTX 4090의 특징란에 **"개인 프로젝트 가성비 최고, NVLink 미지원"**이 나란히 적혀 있습니다 [강의 표]. 단일 GPU 가성비와 분산 확장성이 서로 다른 축이라는 것을 한 줄로 보여주는 표기입니다.

**제 프로젝트에는 해당사항이 적습니다.** 110M 파라미터 모델은 GPU 한 장에 충분히 들어가므로 분산 학습이 필요 없습니다. 이 지표가 중요해지는 것은 LLM 파인튜닝처럼 모델 자체가 안 들어갈 때입니다.

### 9-2. "시간당 비용"이 아니라 "실험당 비용"으로 평가해야 하는 이유

**강의 자료의 비교 표 [강의 표]**

| 구성 | 시간당 비용 | 학습 시간 | 총 비용 |
|---|---|---|---|
| 구세대 GPU 4대 | $24/시간 (저렴) | 72시간 | **~$1,750** |
| 최신 GPU 8대 | $31/시간 (비쌈) | 8시간 | **~$250** |

**숫자를 뜯어보면**

- 시간당 단가: 최신 GPU가 **1.29배 비쌉니다** ($31 ÷ $24)
- 학습 시간: 최신 GPU가 **9배 빠릅니다** (72시간 ÷ 8시간)
- 총 비용: 최신 GPU가 **약 7배 저렴합니다** ($1,750 ÷ $250)

검산하면 $24 × 72시간 = $1,728, $31 × 8시간 = $248로 표의 근삿값과 맞습니다.

**역전이 일어나는 조건**

두 축의 배수를 비교하면 구조가 드러납니다.

> **총비용 배수 = 시간당 단가 배수 ÷ 학습 시간 배수**
> 강의 사례: 1.29 ÷ 9 ≈ **0.14** → 약 1/7, 즉 7배 저렴

즉 **학습 시간 단축 배수가 시간당 단가 상승 배수보다 크면 역전됩니다.** 강의 사례는 1.29배 더 내고 9배 빨라지므로 압도적으로 역전됩니다. 시간당 단가만 보고 구세대 GPU를 고르면 **$1,500을 더 쓰고 64시간을 더 기다리는** 선택이 됩니다 — 돈과 시간 양쪽에서 손해입니다.

**왜 9배나 차이가 나는가**

GPU 대수가 4대 → 8대로 2배지만 속도는 9배입니다. 대수 증가만으로는 설명되지 않습니다. 강의 9.2의 세 지표로 보면:

- **메모리 대역폭** — 최신 서버용 GPU는 HBM을 써서 소비자용 GDDR 대비 2~4배 넓습니다
- **연산 속도** — Tensor Core의 16비트 성능. 강의 GPU 가이드 표에 따르면 H100은 **FP8 지원과 Transformer 최적화 엔진**까지 내장합니다 [강의 표]
- **인터커넥트** — 8대를 쓰려면 GPU 간 통신이 병목이 되는데, NVLink가 있으면 대수에 비례하는 향상이 가능합니다

**그리고 표에 없는 비용이 하나 더 있습니다**

| | 구세대 4대 | 최신 8대 |
|---|---|---|
| 1회 실험 | 72시간 (3일) | 8시간 (하루 안) |
| **반복 주기** | **3일에 한 번** | **하루에 한 번** |

72시간이면 실험을 걸고 3일 뒤에 결과를 봅니다. 하이퍼파라미터를 하나 잘못 넣었으면 3일을 날립니다. 8시간이면 아침에 걸고 퇴근 전에 확인합니다. **엔지니어의 대기 시간은 표의 총비용에 잡히지 않지만 실제로는 가장 비싼 항목입니다.**

**결론**: 강의의 표현대로 **"가장 저렴한 업체에서 가장 성능 좋은 GPU를 빌려 짧게 끝내는 것"**이 가장 경제적입니다.

단, 이 논리에는 전제가 있습니다. **GPU를 충분히 활용할 때만 성립합니다.** 데이터 로딩이 병목이면 H100을 빌려도 놀기만 하므로 학습 시간이 9배 줄지 않고, 그러면 역전 조건이 깨져 비싼 GPU가 그냥 비싼 선택이 됩니다. Ch8.12의 프로파일링으로 **GPU 활용률을 먼저 확인해야** 이 계산이 유효합니다.

### 9-3. 스팟 인스턴스를 안전하게 쓰기 위한 전제 조건

**핵심 전제는 체크포인팅 자동화입니다.** 스팟은 70~90% 저렴하지만 언제든 회수될 수 있으므로, 회수를 **정상적인 사건으로 취급**하는 구조여야 합니다.

**① 주기적 체크포인트 저장**

가중치만이 아니라 **옵티마이저 상태, 스케줄러 상태, 에포크·스텝 번호**까지 저장해야 이어서 학습할 수 있습니다. Adam은 파라미터마다 momentum과 variance를 들고 있어서, 이걸 빼놓고 재개하면 사실상 다른 학습이 됩니다. Lightning의 `ModelCheckpoint`는 이 전부를 기본 저장합니다.

```python
pl.callbacks.ModelCheckpoint(save_last=True, every_n_train_steps=500)
```

`save_last=True`가 특히 중요합니다. "성능이 가장 좋은" 체크포인트는 재개용이 아닙니다. **재개에 필요한 것은 가장 최근 상태**입니다.

**② 재개 로직**

```python
trainer.fit(model, datamodule=data, ckpt_path="last")
```

**③ 체크포인트를 인스턴스 밖에 저장할 것**

강의에 명시되지는 않았지만 실무에서 가장 흔한 실패 지점입니다. **체크포인트를 인스턴스 로컬 디스크에 저장하면, 인스턴스가 회수될 때 디스크도 함께 사라집니다.** S3/GCS 같은 객체 저장소나 별도 마운트 볼륨에 저장해야 합니다. 체크포인팅을 열심히 해놓고 회수와 함께 전부 잃는 경우가 있습니다.

**④ 저장 주기의 트레이드오프**

너무 자주 저장하면 I/O가 학습을 느리게 하고, 너무 드물면 회수 시 잃는 진행분이 커집니다. 대략 **"잃어도 감당 가능한 시간"**을 기준으로 정합니다 — 10분어치를 잃어도 되면 10분 주기입니다.

**⑤ 스팟이 부적합한 경우**

기한이 임박한 최종 학습, 회수 시 재현이 어려운 실험, 인스턴스 확보 자체가 불확실한 시점의 급한 작업에는 온디맨드를 씁니다. **비용 최적화가 일정 리스크로 전환되는 지점**이 있습니다.

> 강의의 지적처럼, Lightning이 이 전부를 기본 지원한다는 사실 자체가 **"Lightning을 쓰는 것이 곧 비용 최적화 전략"**이라는 뜻입니다. 프레임워크 선택이 인프라 비용을 결정합니다.

### 9-4. 실습에서 W&B가 있었다면 편리했을 지점

**직전 과정의 붓꽃 분류 실습을 예로 들면 이렇습니다.**

당시 저는 `RandomForestClassifier(n_estimators=100, random_state=42)`로 학습하고 **정확도 1.0을 확인한 뒤 바로 배포로 넘어갔습니다.** 기록으로 남은 것은 `model.joblib` 파일 하나뿐입니다.

여기서 W&B가 있었다면 달랐을 지점들:

**① 하이퍼파라미터가 코드에만 남았습니다**
`n_estimators=100`을 고른 근거가 없습니다. 50이나 200과 비교해본 적이 없으니, 지금 와서 "왜 100인가"에 답할 수 없습니다. W&B의 `config`는 실행할 때마다 이걸 자동 기록합니다.

**② 정확도 1.0을 의심하지 않았습니다**
전체 데이터로 학습하고 같은 데이터로 점수를 냈으니 1.0이 나오는 게 당연합니다. **이건 성능 지표가 아니라 파이프라인이 돌아간다는 확인일 뿐입니다.** W&B에 학습/검증 곡선을 나란히 기록하는 습관이 있었다면 검증셋이 없다는 사실이 대시보드의 빈칸으로 즉시 드러났을 것입니다. 도구가 부재를 가시화합니다.

**③ 환경 정보가 기록되지 않았습니다**
7-3에서 겪은 scikit-learn 버전 문제가 정확히 이겁니다.

강의가 명시한 것은 **GPU 사용률·메모리 사용량 같은 시스템 메트릭의 자동 수집**입니다. 환경 버전까지 남기려면 `wandb.init(config=...)`에 `sklearn.__version__` 같은 값을 직접 넣거나 `requirements.txt`를 아티팩트로 함께 올리는 식으로 **명시적으로 기록해야 합니다.**

어느 쪽이든 핵심은 같습니다 — **실험 기록이 "결과"만이 아니라 "그 결과가 나온 조건"을 담아야 한다**는 것이고, `model.joblib` 파일 하나만 남기는 것과는 추적성이 다릅니다.

**④ 배포된 모델과 실험의 연결이 끊겼습니다**
지금 GCP에서 돌아가는 컨테이너 안의 모델이 **어느 실험의 산출물인지 기록이 없습니다.** 성능 이상이 생겨도 어떤 학습으로 돌아가야 하는지 알 수 없습니다. Ch12의 "코드 + 데이터 = 모델" 공식에서 세 요소를 잇는 고리가 없는 상태입니다.

**정리하면**, 실험이 한 번뿐이었기에 불편을 못 느꼈지만 **기록이 없다는 사실 자체를 인지하지 못한 것이 진짜 문제**였습니다. 실험이 수십 번으로 늘어나면 그때 도입하기에는 이미 늦습니다 — 지나간 실험은 소급 기록할 수 없기 때문입니다.

# Chapter 10. 데이터 저장과 관리의 기초

### 10-1. 스토리지 계층의 지연 시간 차이가 `num_workers` 설정에 미치는 영향

**연결 고리는 "GPU를 놀리지 않으려면 데이터가 미리 준비돼 있어야 한다"입니다.**

학습 한 스텝은 (a) 디스크에서 데이터를 읽어 전처리하고 (b) GPU에서 연산하는 두 단계입니다. 이 둘이 **순차적으로** 일어나면 GPU는 (a) 동안 놀게 됩니다.

강의의 스토리지 계층 표는 이 차이를 캐시 접근 1ns를 인간의 1초로 환산해 보여줍니다 [강의 표].

| 위치 | 실제 시간 | 체감 시간 | 시사점 |
|---|---|---|---|
| L1/L2 캐시 | 1 ns | **1초** | GPU 연산의 이상적 속도 |
| RAM (메모리) | 100 ns | **~1.5분** | 캐시보다 100배 느림 |
| NVMe SSD 1MB | ~µs 수준 | **~2.5일** | 로컬이라도 메모리보다 훨씬 느림 |
| HDD 1MB | ~ms 수준 | **~수개월** | 물리적 회전에 의한 막대한 지연 |
| 네트워크(S3 등) | ~150 ms | **~수년** | 원격 데이터 접근의 비용 |

**여기서 가장 중요한 줄은 NVMe SSD입니다.** 로컬 SSD조차 체감 2.5일입니다. "데이터를 로컬 디스크에 뒀으니 괜찮다"가 아니라, **로컬에 뒀어도 여전히 메모리 대비 자릿수가 다르므로 prefetch가 필요하다**는 뜻입니다. 네트워크(체감 수년)는 학습 루프에서 직접 읽으면 안 되는 수준입니다.

`num_workers > 0`은 **별도 프로세스가 다음 배치를 미리 읽어두게(prefetch)** 만듭니다. GPU가 배치 N을 연산하는 동안 워커들이 배치 N+1을 준비하므로 (a)가 (b) 뒤에 숨습니다.

**그래서 지연 시간이 클수록 워커가 더 많이 필요합니다.**

| 데이터 위치 | 배치 준비 시간 | 필요한 워커 수 |
|---|---|---|
| 메모리(캐시됨) | 매우 짧음 | 적어도 됨. 0도 가능 |
| 로컬 NVMe SSD | 중간 | CPU 코어 수의 절반~전체 |
| 네트워크 마운트·S3 직접 읽기 | 매우 김 | 많이 필요. 그래도 못 따라잡을 수 있음 |

**핵심 통찰은 "워커를 늘리는 것이 근본 해법이 아닐 수 있다"는 점입니다.** 배치 준비가 GPU 연산보다 근본적으로 느리면 워커를 아무리 늘려도 병목이 남습니다. 그래서 강의가 **"데이터를 GPU 바로 옆의 로컬 디스크로 옮겨라"**고 강조하는 것입니다. `num_workers`는 지연을 숨기는 수단이지 없애는 수단이 아닙니다.

**워커를 무작정 늘리면 안 되는 이유**: 각 워커는 별도 프로세스라 메모리를 따로 씁니다. 너무 많으면 RAM이 부족해지고 프로세스 간 컨텍스트 스위칭 오버헤드가 커집니다. `persistent_workers=True`로 에포크 사이 워커를 유지하면 초기화 비용도 줄일 수 있습니다.

**측정이 먼저입니다.** Ch8.12의 프로파일러에서 `get_train_batch`가 전체의 32%를 차지한다면 데이터 로딩이 병목이라는 뜻이고, 이때 `num_workers`를 조정합니다. **추측으로 조정하지 않습니다.**

### 10-2. "이진 데이터는 S3에, URL만 DB에" 원칙의 이유 / 어겼을 때의 문제

**원칙의 이유는 두 시스템이 잘하는 일이 다르기 때문입니다.**

| | 데이터베이스 | 객체 저장소 |
|---|---|---|
| 잘하는 것 | 구조화된 데이터의 인덱싱·조인·트랜잭션 | 대용량 이진 파일의 저렴한 저장·전송 |
| 비용 | 상대적으로 비쌈 | 저렴 |
| 확장 | 어려움 | 사실상 무한 |

이미지 한 장을 DB에 넣어도 **DB가 할 수 있는 일은 "꺼내는 것"뿐입니다.** 이미지 내용으로 검색하거나 조인할 수 없습니다. 즉 DB의 강점을 전혀 쓰지 못하면서 비싼 저장 공간만 차지합니다.

**어겼을 때 발생하는 문제**

**① 백업과 복제가 마비됩니다.** 이게 가장 아픕니다. DB는 정기적으로 전체 백업하고 복제본에 동기화하는데, 이미지가 들어 있으면 DB 크기가 수십 배로 불어납니다. 백업 시간이 몇 분에서 몇 시간이 되고, 장애 복구 시간(RTO)이 그만큼 늘어납니다. **평소엔 잘 돌아가다가 장애가 났을 때 대가를 치릅니다.**

**② 쿼리 성능이 전반적으로 떨어집니다.** DB는 자주 쓰는 데이터를 메모리 버퍼에 캐싱하는데, 큰 이진 데이터가 이 공간을 밀어냅니다. 이미지와 무관한 다른 쿼리까지 느려집니다.

**③ 커넥션이 오래 점유됩니다.** 큰 이진 데이터를 전송하는 동안 DB 커넥션이 묶입니다. 커넥션 풀은 유한하므로 동시 요청 처리량이 떨어집니다.

**④ 스케일 아웃이 막힙니다.** 이진 데이터가 섞이면 DB 샤딩이 훨씬 복잡해집니다.

**강의의 데이터 포맷 표도 같은 구조를 지지합니다** [강의 표]. `Parquet`의 용도가 **"정형 메타데이터(URL, 라벨 등)"**로 명시되어 있습니다 — 즉 URL을 담는 장부용 포맷이라는 것이 표에 이미 적혀 있습니다. 이진 데이터를 담는 포맷으로는 `HDF5`(대규모 다차원 수치)와 `safetensors`(모델 가중치)가 따로 나뉘어 있습니다.

**제 프로젝트에 적용하면**: 사기 게시글 판단에는 상품 이미지가 중요한 신호입니다(도용된 사진, 다른 게시글과 동일한 이미지). 하지만 이미지는 GCS에 두고 DB에는 `image_url`과 **이미지 해시**만 저장합니다. 해시는 "같은 사진이 여러 계정에서 쓰였는가"를 SQL로 즉시 조회할 수 있게 해주는 구조화된 값이라 DB에 넣는 것이 맞습니다. **원본은 객체 저장소, 검색에 쓰는 파생 값은 DB** — 이 구분이 원칙의 실제 적용 방식입니다.

### 10-3. OLTP vs OLAP — "행 지향 vs 열 지향"과 적합한 쿼리

**저장 구조의 차이**

10개 컬럼을 가진 100만 행 테이블이 있다고 하겠습니다.

- **행 지향(OLTP)**: 한 행의 10개 컬럼이 디스크에 붙어 저장됩니다. 특정 행을 통째로 읽을 때 한 번의 접근으로 끝납니다.
- **열 지향(OLAP)**: 같은 컬럼의 100만 개 값이 붙어 저장됩니다. 한 컬럼만 필요하면 나머지 9개를 건드리지 않습니다.

**적합한 쿼리 — 제 프로젝트 기준**

**OLTP (Postgres)** — 서빙 시점의 조회

```sql
-- 게시글 하나에 대해 모델 입력 피처를 조회
SELECT p.title, p.body, p.price, s.joined_at, s.report_count
FROM posts p JOIN sellers s ON p.seller_id = s.id
WHERE p.id = 8471023;
```
행 하나를 전부 읽습니다. 게시글이 등록될 때마다 실시간으로 호출되므로 **응답 지연이 곧 사용자 경험**입니다. 행 지향이 유리합니다.

**OLAP (BigQuery 등)** — 분석·모니터링

```sql
-- 지난 90일간 카테고리별 사기 신고율
SELECT category, COUNT(*) AS total,
       AVG(CASE WHEN is_fraud THEN 1 ELSE 0 END) AS fraud_rate
FROM posts
WHERE created_at >= CURRENT_DATE - 90
GROUP BY category;
```
수천만 행을 훑지만 **컬럼은 3개만** 씁니다. 열 지향이면 나머지 컬럼을 아예 읽지 않아 I/O가 압도적으로 적습니다. 같은 컬럼의 값들은 성질이 비슷해 압축률도 높습니다.

**왜 하나로 통일할 수 없는가**

같은 데이터를 두 곳에 두는 게 낭비처럼 보이지만, **행 지향에서 위 집계 쿼리를 돌리면 필요 없는 컬럼까지 전부 읽습니다.** 더 중요한 건 이 무거운 쿼리가 실시간 서빙용 DB의 자원을 잡아먹는다는 점입니다 — 분석 쿼리 하나가 사기 탐지 API 전체를 느리게 만들 수 있습니다.

**제 프로젝트에는 둘 다 필요합니다.** 서빙 피처 조회는 OLTP, 드리프트 모니터링과 학습 데이터 추출은 OLAP입니다. 특히 Day 1에서 설계한 "상담사 불일치율을 선행 지표로 감시"하는 작업이 전형적인 OLAP 워크로드입니다.

# Chapter 11. 데이터 레이블링과 품질 관리

### 11-1. 레이블링 최소화 4가지 전략 요약 / 내 프로젝트에 적용 가능한 것

**각 전략 한 문장 요약**

| 전략 | 한 문장 |
|---|---|
| **자기주도 학습** | 데이터 자체의 구조(다음 토큰, 마스킹된 단어)를 정답으로 삼아 레이블 없이 학습한다 |
| **데이터 증강** | 원본의 본질적 의미는 유지하고 표면적 특성만 바꿔 학습 데이터를 불린다 |
| **합성 데이터** | 알고리즘이나 생성 모델로 데이터를 만들되, 생성 시점에 정답을 이미 알고 있으므로 레이블링 비용이 0이다 |
| **사용자 피드백** | 클릭·수정·신고 같은 사용자 행동 자체를 암묵적 레이블로 전환한다 |

**내 프로젝트에 적용 가능한가 — 하나씩 검토**

**④ 사용자 피드백 → 주력으로 채택**

가장 강력합니다. 구매자의 **신고**, 상담사의 **검토 결과와 사유 코드**, 거래 **분쟁 접수**가 전부 별도 비용 없이 레이블이 됩니다. Day 1에서 설계한 데이터 플라이휠이 그대로 레이블링 전략입니다.

단, Day 1에서 짚은 한계가 그대로 남습니다. **신고되지 않은 게시글이 정말 정상인지는 알 수 없습니다.** 그래서 저위험 구간에서 무작위 표본을 강제로 검토 큐에 섞어 음성 레이블의 신뢰도를 확보해야 합니다.

**① 자기주도 학습 → 보조로 채택**

레이블 없는 게시글 원문은 무한히 있습니다. 이걸로 **도메인 적응 사전학습**(MLM 추가 학습)을 하면, 일반 한국어로 학습된 인코더가 중고거래 특유의 표현("네고 가능", "직거래만", 상품 은어)을 이해하게 됩니다. 레이블이 한 건도 필요 없으면서 후속 파인튜닝의 출발점을 크게 개선합니다.

**② 데이터 증강 → 제한적으로만**

**일반적인 텍스트 증강 기법이 이 도메인에서는 위험합니다.**
- 유의어 교체: 사기 은어는 특정 표현 자체가 신호라, 유의어로 바꾸면 신호가 사라집니다.
- 역번역(한→영→한): 은어와 오탈자가 정상 표현으로 "교정"되어 버립니다. **탐지하려는 특징을 증강이 지워버리는 셈입니다.**

대신 **적대적 회피 패턴을 모사하는 증강**은 매우 유효합니다. 사기꾼이 필터를 피하려고 쓰는 변형 — 공백 삽입("선입금" → "선 입 금"), 기호 삽입("계좌" → "계·좌"), 유사 문자 치환("입금" → "ㅇl금"), 숫자 표기 변경("010" → "공일공") — 을 프로그램으로 생성해 학습에 넣습니다. **일반적 증강이 아니라 도메인 특성에 맞춘 증강이어야 합니다.**

**③ 합성 데이터 → 초기 콜드스타트 구간에만**

희귀 사기 유형처럼 실제 사례가 적은 클래스를 LLM으로 보강할 수 있습니다. 다만 주의점이 큽니다(11-4에서 상술).

**우선순위: ④ 주력 → ① 보조 → ② 도메인 특화 형태로만 → ③ 희귀 유형 보강용**

### 11-2. "골드 표준 데이터셋"은 왜 필요한가 / 없이 외주를 맡기면

**골드 표준은 엔지니어가 직접 레이블링한 200~500건 규모의 기준 데이터셋입니다.** 세 가지 역할을 합니다.

**① 레이블러 품질의 측정 자**

외주 레이블러의 작업물이 정확한지 판단하려면 **정답을 아는 데이터**가 있어야 합니다. 골드 표준을 작업 물량에 몰래 섞어 넣고 일치율을 보면, 레이블러별 품질을 정량적으로 잡아낼 수 있습니다. 이게 없으면 품질 평가가 "느낌"이 됩니다.

**② 가이드라인의 모호함을 드러내는 장치**

강의의 1단계가 "직접 100개 이상 레이블링해 보라"인 이유가 이겁니다. **직접 해보면 반드시 판단이 막히는 케이스가 나옵니다.** 제 프로젝트에서 실제로 문제가 될 것들:

- 시세의 40%에 올라온 물건 — 사기인가, 급처분인가?
- "선입금 후 발송"은 사기 신호지만, 공동구매 게시글에서는 정상 관행이다
- 판매자가 사기 이력이 있지만 이번 게시글 자체는 정상이라면?

이런 경계 케이스를 만나면서 가이드라인이 구체화됩니다. **골드 표준을 만드는 행위가 곧 문제 정의를 정밀하게 만드는 과정입니다.**

**③ 태스크 자체가 성립하는지에 대한 검증**

엔지니어 두 명이 같은 200건을 레이블링했는데 일치율이 낮게 나온다면, 레이블러의 성실성 문제가 아닙니다. 강의가 짚은 대로 **가이드라인이 모호하거나 태스크 자체의 정의가 잘못된 것**이므로 **둘 다 재검토해야 합니다.**

- **가이드라인이 모호한 경우** — 경계 케이스에 대한 규정을 추가하면 해결됩니다 (예: "시세 대비 몇 % 이하부터 의심으로 볼 것인가"를 수치로 명시)
- **태스크 정의가 잘못된 경우** — 규정을 아무리 더해도 합의가 안 됩니다. 이때는 태스크를 다시 쪼개야 합니다 — Day 1의 "사기인가?" 대신 "선입금 요구 문구가 있는가?"로 분해하는 접근입니다

둘을 구분하는 방법은 **불일치한 건들을 놓고 두 사람이 토론해 보는 것**입니다. 규정을 하나 추가해서 합의가 되면 전자, 토론해도 갈리면 후자입니다. 어느 쪽이든 **사람도 합의 못 하는 것을 모델이 학습할 수는 없다**는 결론은 같습니다.

**골드 표준 없이 외주를 맡기면 벌어지는 일**

1. **레이블러마다 다른 기준으로 작업합니다.** 강의의 여우 예시처럼("머리만 박스를 치는가, 가려진 몸까지 추측하는가") 사람마다 해석이 갈립니다. 결과물은 **일관성 없는 레이블의 혼합**이고, 모델은 서로 모순되는 신호를 학습합니다.

2. **문제를 늦게 발견합니다.** 5만 건을 다 받고 나서야 품질 이상을 알아챕니다. 이미 비용은 다 지불했고, 다시 하려면 처음부터입니다.

3. **모델 성능이 나쁠 때 원인을 특정할 수 없습니다.** 모델이 부족한 건지, 레이블이 오염된 건지 구분할 방법이 없습니다. **아키텍처를 몇 주간 붙잡고 있는데 사실은 레이블 문제인** 상황이 생깁니다.

4. **레이블 노이즈가 성능을 제한합니다.** 노이즈가 많으면 모델이 잘못된 신호를 학습하고, 더 나쁘게는 **평가 결과 자체의 신뢰도가 떨어집니다** — 평가셋 레이블도 같이 오염되어 있으므로 지표가 좋아진 것이 실제 개선인지 노이즈에 맞춘 것인지 구분되지 않습니다. 그런데 이 제약의 존재를 모르니 계속 모델만 개선하려 듭니다. (노이즈 비율이 곧 성능 상한이 되는 것은 아니지만, 실질적인 향상 여지를 좁히는 것은 분명합니다.)

### 11-3. 약지도 학습이 수동 레이블링 대비 갖는 "유지보수" 관점의 장점

**레이블 체계가 바뀔 때 무슨 일이 벌어지는가 — 두 방식 비교**

제 프로젝트에서 실제로 일어날 법한 변경을 가정하겠습니다. 처음에는 **사기 / 정상** 이진 분류였는데, 운영하다 보니 "판단 보류" 구간이 필요해져 **사기 / 의심 / 정상** 3분류로 바꾸기로 했습니다.

**수동 레이블링의 경우**

- 이미 레이블링한 5만 건 전부를 **다시 봐야 합니다.** "정상"으로 표시된 것 중 어느 것이 "의심"인지 기존 레이블만 봐서는 알 수 없습니다.
- 외주 비용을 다시 지불하고, 가이드라인을 다시 쓰고, 몇 주를 기다립니다.
- 그 사이 프로젝트는 멈춥니다.
- **이 비용 때문에 레이블 체계 변경 자체를 포기하는 일이 흔합니다.** 더 나은 문제 정의를 알면서도 못 바꾸는 상황 — 이게 진짜 손실입니다.

**약지도 학습의 경우**

- 레이블링 함수는 **코드**입니다. 기권값(-1)을 반환하던 구간을 "의심"으로 매핑하도록 함수를 수정합니다.
- 다시 실행합니다. 수백만 건의 레이블이 **몇 분 만에** 갱신됩니다.
- 비용은 엔지니어 몇 시간입니다.

**핵심 차이는 "레이블이 자산인가, 파생물인가"입니다.**

수동 레이블링에서 레이블은 **비싸게 산 자산**이라 버리기 아깝고, 그래서 기준을 바꾸기 어렵습니다. 약지도 학습에서 레이블은 **함수를 실행하면 언제든 다시 나오는 파생물**입니다. 진짜 자산은 레이블이 아니라 **레이블링 함수(코드)**이고, 코드는 Git으로 버전 관리되며 리뷰와 테스트의 대상이 됩니다.

**제 프로젝트에서 특히 잘 맞는 이유**

**기존 룰 300개가 사실상 이미 레이블링 함수입니다.** Day 1에서 이 룰들을 "관리 불가능해진 부채"로 봤는데, 약지도 학습 관점에서 보면 **폐기할 대상이 아니라 재활용할 자산**입니다. 각 룰을 레이블링 함수로 감싸고, Snorkel이 룰 간 충돌과 각 룰의 정확도를 확률 모델로 학습해 최종 레이블을 만듭니다.

```python
def lf_prepayment_only(post):
    return FRAUD if "선입금만" in post.body else ABSTAIN

def lf_new_seller_low_price(post):
    if post.seller_age_days < 7 and post.price < post.market_price * 0.5:
        return FRAUD
    return ABSTAIN

def lf_verified_seller(post):
    return NORMAL if post.seller_transaction_count > 50 else ABSTAIN
```

**추가 이점**: 사기 수법이 바뀌면 함수를 하나 추가하고 다시 돌리면 됩니다. Day 1에서 "적대적 드리프트가 가장 위협적"이라고 했는데, 약지도 학습은 **드리프트 대응 주기를 몇 주에서 몇 시간으로 줄여줍니다.** 이 도메인에서는 유지보수성이 곧 방어력입니다.

### 11-4. LLM 합성 데이터가 효과적인 상황과 주의할 점

**효과적인 상황**

**① 콜드 스타트 — 실제 데이터가 아직 없을 때**
서비스 출시 전이거나 신규 카테고리를 여는 시점에는 학습 데이터가 없습니다. LLM으로 초기 데이터를 만들어 v0 모델을 띄우고, 실제 데이터가 쌓이면 교체합니다.

**② 희귀 클래스 보강**
전체의 0.1%밖에 없는 사기 유형은 실제 데이터를 모으는 데 몇 달이 걸립니다. LLM으로 변형을 생성해 그 클래스의 표본을 늘립니다.

**③ 지시-응답 형식의 데이터**
강의의 예처럼 "고객 문의에 대한 친절한 응답 1000개"는 정답이 하나가 아니고 품질 판단이 비교적 쉬워서 LLM 생성이 잘 맞습니다.

**④ 프라이버시 제약이 있을 때**
실제 게시글에는 개인정보가 있어 외부 레이블러에게 보내기 어렵습니다. 합성 데이터는 이 제약을 우회합니다.

**주의할 점 — 제 도메인에서는 특히 심각합니다**

**① 실제 분포와 다릅니다 (가장 근본적)**
LLM에게 "사기 게시글을 만들어줘"라고 하면 **"전형적인" 사기 게시글**을 만듭니다. 그런데 실제 사기꾼은 탐지를 피하려고 전형성을 일부러 피합니다. **합성 데이터로 학습한 모델은 티 나는 사기만 잘 잡고, 정작 위험한 교묘한 사기는 놓칠 수 있습니다.** Day 1에서 걱정한 "작은 문제 해결" 실패 유형으로 이어집니다.

**② 다양성이 부족합니다**
같은 프롬프트로 1000개를 생성하면 표면적 표현만 다르고 구조가 비슷한 데이터가 나옵니다. 모델이 **합성 데이터 특유의 문체 패턴**을 학습해 실제 데이터에서 무너질 수 있습니다.

**③ 모델 붕괴(Model Collapse) 위험**
LLM이 만든 데이터로 학습한 모델의 출력을 다시 학습 데이터로 쓰는 순환이 생기면, 분포가 점점 좁아지며 실제 세계에서 멀어집니다.

**④ LLM의 편향이 그대로 주입됩니다**
LLM이 특정 유형의 판매자나 상품군을 사기와 연관 짓는 편향이 있다면, 합성 데이터가 그 편향을 증폭합니다. **Day 1의 윤리 체크포인트(특정 집단에 불공정한 영향)와 직결됩니다.**

**⑤ 검증이 필수인데, 검증에도 비용이 듭니다**
"합성 데이터의 품질을 검증하는 단계는 반드시 필요하다"는 강의의 단서가 핵심입니다. 그런데 검증하려면 결국 사람이 봐야 하므로, **레이블링 비용을 0으로 만들지는 못합니다.** 줄일 뿐입니다.

**제 결론**: 합성 데이터는 **주력이 아니라 보조**입니다. 실제 신고·검토 데이터가 확보되기 전 구간에서만 쓰고, 실제 데이터가 쌓이면 비중을 낮춥니다. 그리고 **평가셋에는 절대 합성 데이터를 쓰지 않습니다** — 평가는 반드시 실제 분포에서 해야 합니다.

# Chapter 12. 데이터 버전 관리와 워크플로우 자동화

### 12-1. 내 현재 프로젝트는 어느 레벨인가 / 한 단계 올리려면

**직전 과정에서 실제로 만든 붓꽃 분류 프로젝트를 기준으로 정직하게 평가하면 — Level 0(무관리)입니다.**

현재 상태를 뜯어보면:

| 요소 | 상태 |
|---|---|
| 학습 데이터 | `load_iris()`로 매번 새로 불러옴. 스냅샷 없음 |
| 학습 코드 | `train.py`로 남아 있음 ✅ |
| 시드 | `random_state=42` 고정 ✅ |
| 학습된 모델 | `model.joblib` — 언제, 어떤 데이터로 만들었는지 기록 없음 |
| 모델과 데이터의 연결 | **없음** |

sklearn 내장 데이터셋이라 우연히 재현되는 것뿐이고, **구조적으로는 아무것도 관리되고 있지 않습니다.** 실제 데이터였다면 `model.joblib`이 어떤 데이터에서 나왔는지 영영 알 수 없습니다.

**Level 1(스냅샷)로 올리려면**

학습할 때마다 사용한 데이터를 `data/2026-08-27/`에 복사하고, 모델 파일명에 그 날짜를 넣어 대응을 남깁니다. 학습 스크립트가 자동으로 하도록 몇 줄만 추가하면 됩니다.

**Level 2(코드로서의 데이터)로 올리려면 — 사기 탐지 프로젝트 기준**

이쪽이 실질적으로 필요한 목표입니다.

1. **게시글 원문은 DB/객체 저장소에 그대로 둡니다.** 옮기지 않습니다.
2. **장부(manifest)를 만듭니다.** `post_id`, `label`, `labeled_by`, `labeled_at`, `guideline_version` 컬럼을 가진 Parquet 파일입니다.
3. **장부를 Git LFS로 커밋합니다.** 학습 실행마다 어떤 장부 커밋을 썼는지 W&B config에 기록합니다.

**여기서 제 도메인 특유의 이점이 하나 있습니다.** 게시글 본문에는 개인정보가 있어 **Git에 원문을 넣으면 안 됩니다.** 장부 방식은 ID와 레이블만 담으므로 개인정보가 저장소에 남지 않습니다. **Level 2가 재현성뿐 아니라 규정 준수 관점에서도 정답**인 셈입니다.

**Level 3(DVC)는 아직 필요 없습니다.** 강의의 권고대로 대부분의 팀에는 Level 2가 실용적이고, **가장 중요한 것은 Level 0에서 벗어나는 것**입니다.

### 12-2. "코드 + 데이터 = 모델" — 데이터 버전 관리 없이 롤백을 시도하면

**구체적 시나리오**

**8월 1일** — 사기 탐지 모델 v3를 배포합니다. 일별 Recall@2000 평균이 v2보다 4%p 개선되어 좋은 릴리스로 보입니다.

**8월 12일** — 사기대응팀에서 이상을 보고합니다. **"전자기기 카테고리의 사기가 요즘 잘 안 걸린다."** 확인해 보니 전체 지표는 여전히 좋은데 전자기기 카테고리만 재현율이 급락했습니다. 전체 평균이 카테고리별 악화를 가리고 있었습니다.

**8월 13일** — 코드를 v2 시점 커밋으로 되돌리고 재학습합니다. **그런데 성능이 복구되지 않습니다.**

**원인** — 7월 중순에 레이블링 가이드라인이 개정되었습니다. "미개봉 새 제품을 시세보다 크게 낮게 판매"하는 유형을 기존에는 사기로 분류했는데, 정상 급처분 사례가 많다는 상담팀 의견에 따라 정상으로 재분류했습니다. **그리고 그 기준으로 기존 레이블을 소급 수정했습니다.**

즉 v2 코드가 학습했던 데이터는 이미 존재하지 않습니다.

**여기서 무슨 일이 벌어지는가**

**① 롤백이 롤백이 아닙니다.** `v2 코드 + 8월 데이터`는 `v2 코드 + 7월 데이터`와 다른 모델입니다. 되돌렸다고 생각하지만 사실 **새로운 조합을 처음 만든 것**입니다.

**② 원인 규명이 불가능합니다.** 성능 저하가 (a) 코드 변경 (b) 레이블 기준 변경 (c) 실제 사기 패턴 변화 중 무엇 때문인지 분리할 수 없습니다. 하나씩 고정해가며 실험해야 하는데, **데이터를 과거 상태로 고정하는 것이 불가능하므로 그 실험 자체를 설계할 수 없습니다.**

**③ 무엇을 잃었는지조차 모릅니다.** 소급 수정이 몇 건에 영향을 줬는지, 그게 전자기기 카테고리에 집중되었는지 알 수 없습니다. 아마 이게 원인이겠지만 **증명할 수 없습니다.**

**④ 시간이 흐를수록 나빠집니다.** 이런 소급 수정이 몇 번 더 쌓이면 데이터의 역사가 완전히 사라집니다.

**데이터가 버전 관리되었다면**

`git checkout <7월 장부 커밋>` 한 번으로 그때의 레이블 상태가 복원됩니다. 그리고 두 장부를 diff하면 **"7월 중순에 전자기기 카테고리 1,200건의 레이블이 사기→정상으로 바뀜"**이 즉시 보입니다. 원인 규명이 몇 주에서 몇 분이 됩니다.

**Day 1의 CACE와 연결**: "무엇 하나를 바꾸면 전부가 바뀐다"는 성질 때문에 ML에서는 **변경 이력이 곧 디버깅 능력**입니다. 롤백 단위가 코드가 아니라 (코드 + 데이터 + 가중치) 세트여야 하는 이유입니다.

### 12-3. Level 2 "장부" 비유를 내 언어로 다시 설명하면

**창고와 재고 장부로 바꿔 보겠습니다.**

큰 창고에 물건 수십만 개가 선반에 놓여 있습니다. 이게 **객체 저장소(S3/GCS)**입니다. 물건 자체는 크고 무거워서 옮기기 어렵고, 옮길 이유도 없습니다.

**장부**에는 물건이 아니라 이렇게만 적습니다.

> *"이번 달 판매용 목록: A-3 선반 7번 물건, B-1 선반 22번 물건, ..."*

장부는 종이 몇 장이면 됩니다. 이게 **Parquet 파일이고 Git으로 관리**합니다.

강의 자료의 삽화가 이 구조를 한 문구로 요약합니다 — **"가벼운 추적, 무거운 데이터"**, 그리고 부제가 **"메타데이터 파일과 대용량 데이터 사이의 연결"**입니다. 추적하는 것(장부)은 가볍고, 추적당하는 것(창고)은 무겁습니다.

**핵심은 이겁니다.** 지난달 재고 구성을 확인하고 싶으면 창고를 통째로 복사해둘 필요가 없습니다. **지난달 장부를 꺼내면 됩니다.** 물건은 창고에 그대로 있으니, 장부가 가리키는 대로 다시 찾으면 그때의 목록이 복원됩니다.

**Level 1(스냅샷)이 왜 나쁜지도 이 비유로 설명됩니다.** Level 1은 매달 **창고를 통째로 하나씩 더 짓는 것**입니다. 재현은 되지만 창고 짓는 비용이 감당이 안 됩니다.

**제 프로젝트에 대입하면**

- **창고** = 게시글 원문이 들어 있는 DB와 이미지가 든 GCS 버킷
- **장부** = `post_id`, `label`, `labeled_by`, `labeled_at`을 담은 Parquet 파일
- **장부의 버전** = Git 커밋

12-2의 사고가 났을 때, 7월 장부와 8월 장부를 나란히 놓고 무엇이 바뀌었는지 보면 됩니다. **창고는 건드리지 않았고, 바뀐 건 목록뿐이니까요.**

**한 가지 덧붙이면**, 이 비유에는 장부가 다루지 못하는 부분이 있습니다. 창고의 물건 자체가 바뀌면(게시글이 수정되거나 삭제되면) 장부가 가리키는 대상이 달라집니다. 그래서 실무에서는 **원본을 불변(immutable)으로 다루거나 내용 해시를 장부에 함께 적어** 이를 방지합니다.

### 12-4. 워크플로우 자동화가 필요해지는 시점 / 스크립트로 충분한 경우와의 구분

**단순 스크립트로 충분한 경우**

| 조건 | 설명 |
|---|---|
| 단계가 순차적 | 앞에서 뒤로 한 줄이면 의존성 그래프가 필요 없음 |
| 실행 빈도가 낮음 | 주 1회 정도면 사람이 실행하거나 cron으로 충분 |
| 실패해도 처음부터 재실행 가능 | 전체가 10분이면 부분 재시도가 필요 없음 |
| 단일 머신에서 완결 | 분산 조율이 필요 없음 |
| 상태를 볼 사람이 나 하나 | 대시보드가 필요 없음 |

**전문 도구(Airflow 등)가 필요한 경우**

| 조건 | 설명 |
|---|---|
| **의존성이 그래프 형태** | 여러 소스를 각각 처리해 나중에 합치는 구조. 병렬 가능한 부분과 순서를 지켜야 하는 부분이 섞임 |
| **부분 재시도가 필요** | 4단계 중 3단계에서 실패했을 때 1~2를 다시 돌리기엔 너무 비쌈. **이게 가장 강력한 도입 사유입니다** |
| 스케줄 실행 + 실패 알림 | 매일 새벽 실행되고 실패 시 담당자에게 알려야 함 |
| **백필(backfill)이 필요** | 로직을 고친 뒤 지난 30일치를 재처리해야 하는 상황. 스크립트로는 매우 번거로움 |
| 여러 사람이 상태를 봐야 함 | "어제 파이프라인 돌았나?"에 대시보드로 답할 수 있어야 함 |

**제 프로젝트의 시점 판단**

**초기(PoC~6개월)는 스크립트로 갑니다.** 주 1회 수동 재학습이고, 단계는 "데이터 추출 → 레이블 조인 → 학습 → 평가"로 순차적이며, 전체가 몇 시간이면 끝납니다. cron + 실패 시 슬랙 알림 정도면 충분합니다.

**Airflow가 필요해지는 신호**는 구체적으로 이렇습니다.

1. 재학습이 **일 단위**로 바뀌어 사람이 챙길 수 없게 될 때
2. **데이터 소스가 늘어날 때** — 게시글 DB, 신고 로그, 상담사 검토 DB, 이미지 해시 배치가 각각 다른 시각에 준비되고, 준비된 것부터 처리해야 할 때
3. **학습이 몇 시간 단위가 되어** 뒷단계 실패 시 앞단계 재실행 비용이 실질적으로 아파질 때
4. **백필 요구가 생길 때** — 레이블링 가이드라인을 고쳤으니 지난 3개월치를 다시 처리해야 하는 상황

**강의의 경고를 잊지 않아야 합니다.** 하둡 26분 vs 유닉스 명령어 70초 사례는 **도구의 오버헤드가 이득보다 클 수 있다**는 뜻입니다. Airflow도 마찬가지로 배포·운영·디버깅 비용이 있습니다. 제 프로젝트 규모에서 파이썬 스크립트 한 개로 되는 일을 DAG로 만들면, **파이프라인을 고치는 것보다 Airflow를 고치는 데 시간을 더 쓰게 됩니다.**

Day 1의 "당신은 구글이 아니다"와 정확히 같은 원칙입니다. 판단 기준도 같습니다 — **"이 도구가 없어서 지금 무엇이 막혔는가?"**에 구체적으로 답할 수 있을 때 도입합니다.

# Day 2 통합 체크포인트

### 통합-1. 환경 점검 — 재현 가능한 환경이었나 / 팀원에게 전달하려면 어떤 파일이 필요한가

**직전 과정의 붓꽃 배포 프로젝트를 정직하게 점검하면 — 절반만 재현 가능합니다.**

| 구간 | 재현 가능? | 근거 |
|---|---|---|
| **서빙 환경** | ✅ 대체로 | `Dockerfile` + `requirements.txt`(scikit-learn 핀 고정). Docker 이미지가 Docker Hub에 올라가 있어 digest로 정확히 같은 이미지를 받을 수 있음 |
| **학습 환경** | ❌ 안 됨 | 로컬 Python 3.14 + 시스템에 깔려 있던 sklearn 1.9.0으로 `train.py`를 실행. **어떤 환경이었는지 어디에도 기록이 없음** |
| **모델 산출물** | ⚠️ 우연히 | `random_state=42` 고정 + sklearn 내장 데이터셋이라 우연히 재현됨. 실제 데이터였다면 불가능 |

**가장 위험한 지점**: 서빙 컨테이너의 sklearn 버전은 고정했지만, **모델을 만든 학습 환경의 버전은 고정하지 않았습니다.** 두 버전이 어긋나면 7-3에서 짚은 문제가 그대로 발생합니다. 지금은 우연히 둘 다 1.9.0일 뿐입니다.

**팀원에게 동일한 환경을 전달하려면 필요한 파일**

**① 환경 정의**
- `requirements.in` — 직접 쓰는 의존성과 의도
- `requirements.txt` — 컴파일된 전체 잠금 (해시 포함)
- `Dockerfile` — 베이스 이미지 태그를 `python:3.13-slim` 대신 **digest로 고정**해야 완전합니다. 태그는 나중에 다른 이미지를 가리킬 수 있습니다
- **학습용 환경 파일 별도** — 서빙과 학습은 의존성이 다릅니다. 학습에는 sklearn·pandas가, 서빙에는 fastapi·uvicorn이 필요합니다

**② 코드**
- `train.py`, `main.py`
- `Makefile` — `make install`, `make train`, `make serve` 한 줄로 실행되게

**③ 재현에 필요한 메타데이터** (지금 완전히 빠져 있는 부분)
- 학습 데이터의 버전 또는 장부 (Ch12 Level 2)
- 랜덤 시드
- 학습 시점의 환경 정보 — W&B `config`에 라이브러리 버전을 직접 넣어 기록 (자동 수집되는 것은 시스템 메트릭 쪽입니다)

### 통합-2. 코드 리팩토링 계획 — Lightning으로 옮긴다면

붓꽃 프로젝트는 scikit-learn 기반이라 Lightning 대상이 아닙니다. **사기 탐지 텍스트 분류 모델**을 기준으로 구상합니다.

**`LightningModule`로 가는 것 — "무엇을" 학습시킬 것인가**

| 메서드 | 들어갈 내용 |
|---|---|
| `__init__` | KoELECTRA 인코더 + 분류 헤드, 클래스 가중치 적용한 손실 함수, `save_hyperparameters()` |
| `forward` | `input_ids`, `attention_mask` → logits |
| `_shared_step` | 배치 언팩 → forward → loss → **사기 확률 산출** (8-3 참조) |
| `training_step` | loss 반환, 스텝 단위 로깅 |
| `validation_step` | 확률·정답·**게시글 날짜**를 누적만 함 (배치 단위로는 순위를 매길 수 없음) |
| `on_validation_epoch_end` | **날짜별로** 상위 2,000건을 뽑아 Recall 을 구하고 평균 → `val_recall_at_2000` 로깅 |
| `test_step` | 최근 30일 데이터에서 슬라이스별(카테고리·신규가입 여부) 지표 |
| `configure_optimizers` | AdamW(lr=2e-5) + **Warmup → Cosine Decay**, `interval: "step"` |

**`Trainer` 설정으로 가는 것 — "어떻게" 학습시킬 것인가**

```python
trainer = pl.Trainer(
    accelerator="gpu", devices=1,
    precision="bf16-mixed",            # L40S(Ada) 는 BF16 지원 — 통합-5 의 비용 가정과 일치
    max_epochs=5,                      # 파인튜닝은 에포크가 적음
    gradient_clip_val=1.0,             # 트랜스포머 안정화
    val_check_interval=0.25,           # 에포크당 4회 검증 (과적합이 빠름)
    callbacks=[
        pl.callbacks.ModelCheckpoint(
            monitor="val_recall_at_2000", mode="max",   # ← val_loss 아님
            save_top_k=3, save_last=True,               # ← 스팟 대비
        ),
        pl.callbacks.EarlyStopping(
            monitor="val_recall_at_2000", mode="max", patience=3
        ),
        pl.callbacks.LearningRateMonitor(logging_interval="step"),
    ],
    logger=pl.loggers.WandbLogger(project="fraud-detection"),
)
```

**분리 기준을 한 문장으로**: **"모델을 바꾸면 결과가 달라지는 것"은 LightningModule에, "모델과 무관하게 학습을 빠르고 안정적으로 만드는 것"은 Trainer에** 넣습니다. 혼합 정밀도나 그래디언트 클리핑은 모델이 무엇이든 적용 가능하므로 Trainer 쪽입니다.

**설계상 특히 신경 쓴 두 가지**

0. **정밀도는 `bf16-mixed`.** 강의 8.8이 짚은 대로 Ampere 이상 GPU는 BF16을 지원하고 FP16보다 수치적으로 안정적입니다. 통합-3에서 고른 L40S(Ada Lovelace)가 여기 해당하므로 `"16-mixed"`(FP16)가 아니라 `"bf16-mixed"`로 명시했습니다. **비용 시뮬레이션의 정밀도 가정과 코드가 같은 값을 가리켜야 합니다.**
1. **`monitor`를 `val_loss`가 아니라 `val_recall_at_2000`으로.** loss가 최소인 체크포인트와 우리가 원하는 지표가 최대인 체크포인트는 다릅니다. 클래스 불균형이 심할수록 더 벌어집니다.
2. **`save_last=True`.** 9-3에서 정리한 스팟 인스턴스 재개를 위한 것입니다. 최고 성능 체크포인트는 재개용이 아닙니다.

강의의 정리대로 대형 클라우드 대비 1/2~1/3 수준이고, 실험·프로토타이핑 용도에 가성비가 가장 좋습니다.

### 통합-4. 데이터 전략 — 확보 방법, 레이블링 최소화, 버전 관리 시작 레벨

**① 데이터를 어떻게 확보할 것인가**

**신규 수집은 필요 없습니다.** 필요한 데이터가 이미 사내에 전부 있습니다.

| 소스 | 내용 | 역할 |
|---|---|---|
| 게시글 DB | 제목·본문·가격·카테고리·이미지 URL | 입력 피처 |
| 판매자 테이블 | 가입일, 거래 횟수, 과거 제재 이력 | 입력 피처 |
| 신고 이력 | 구매자 신고 | **양성 레이블** |
| 상담사 검토 로그 | 사기 확정/정상 + 사유 코드 | **고품질 레이블** |
| 분쟁·환불 접수 | 거래 후 문제 발생 | 지연된 양성 신호 |

**콜드 스타트가 아니라는 것이 이 프로젝트의 가장 큰 강점**입니다. Day 1의 실현 가능성 평가에서 높은 점수를 준 근거이기도 합니다.

**다만 Day 1에서 짚은 구조적 결함이 그대로 남습니다** — 신고되지 않은 게시글이 정상인지 미탐인지 구분되지 않으므로, **음성 레이블이 오염되어 있습니다.** 그래서 저위험 구간에서 무작위 표본을 강제로 검토 큐에 섞어 깨끗한 음성 표본을 확보해야 합니다. 이건 데이터 확보 계획의 일부로 처음부터 넣어야 합니다.

**② 레이블링 최소화 전략 — 적용 가능한 것**

| 우선순위 | 전략 | 적용 방식 |
|---|---|---|
| 1 | **약지도 학습 (Snorkel)** | **기존 룰 300개를 레이블링 함수로 재활용.** 폐기 대상이 아니라 자산 |
| 2 | **사용자 피드백** | 신고·검토 결과·분쟁 접수를 자동으로 레이블 파이프라인에 연결 |
| 3 | **자기주도 학습** | 레이블 없는 게시글 코퍼스로 도메인 적응 사전학습(MLM) |
| 4 | **능동적 학습** | 일 2,000건 중 **일부(예: 200건)를 탐색 몫으로 떼어** 모델이 가장 불확실해하는 건에 배정 — 나머지는 위험도 상위 순으로 운영 목적에 사용 |
| 5 | 데이터 증강 | 일반 기법은 위험. **적대적 회피 패턴 모사**만 (11-1 참조) |
| 6 | 합성 데이터 | 희귀 유형 보강용으로만. 평가셋에는 사용 금지 |

**4번은 설계에 주의가 필요합니다.** 상담사 검토 용량은 고정된 희소 자원이고, 이 자원은 두 목적이 경쟁합니다.

| 목적 | 무엇을 큐에 넣는가 |
|---|---|
| **운영** — 오늘 사기를 최대한 잡는다 | 위험도가 **높은** 순 |
| **학습** — 모델을 가장 빨리 개선한다 | 모델이 가장 **불확실해하는** 것 |

**두 기준이 다릅니다.** 모델이 확신하는 고위험 건은 잡는 데는 좋지만 학습에 새 정보를 거의 안 줍니다. 반대로 불확실한 경계 케이스는 학습에는 값지지만 실제 사기 적중률은 낮습니다. 그래서 **불확실한 건을 큐 상단에 올리면 그날의 검거 실적이 떨어집니다.**

현실적인 해법은 **탐색 몫을 따로 떼는 것**입니다 — 일 2,000건 중 1,800건은 위험도 상위 순으로 운영에 쓰고, 200건(10%)만 능동적 학습과 무작위 표본에 배정합니다. Day 1에서 "저위험 구간 무작위 표본을 강제로 섞어야 한다"고 한 것과 같은 예산에서 나갑니다.

**이 비율 자체가 운영 지표와 학습 속도 사이의 트레이드오프**이고, PoC에서 조정할 대상입니다.

**③ 데이터 버전 관리 — Level 2부터 시작**

Level 1(스냅샷)을 건너뜁니다. 이유는 세 가지입니다.

1. **게시글 원문은 어차피 DB에 있고 옮길 이유가 없습니다.** 스냅샷은 이미 있는 것을 복사하는 낭비입니다.
2. **개인정보 때문에 원문을 Git에 넣을 수 없습니다.** ID와 레이블만 담는 장부 방식이 필수입니다.
3. **레이블 기준이 자주 바뀔 것이 예상됩니다.** 12-2의 사고를 방지하려면 처음부터 장부를 버전 관리해야 합니다.

**구체적 실행**

```
data/
  manifest/
    labels_2026-08.parquet   # post_id, label, labeled_by, labeled_at, guideline_version
  guidelines/
    v1.md, v2.md             # 레이블링 가이드라인도 함께 버전 관리
```

`guideline_version` 컬럼이 핵심입니다. **레이블이 어떤 기준으로 붙었는지를 데이터 안에 기록**해두면, 12-2 같은 상황에서 기준 변경의 영향 범위를 SQL 한 줄로 확인할 수 있습니다.

### 통합-5. 비용 시뮬레이션 — GPU 시간 추산과 "시간당" vs "실험당" 비교

> 단가와 소요 시간은 모두 **가정치**입니다. 강의 표에서 인용한 값에는 [강의 표]를 붙였습니다.

**전제**

| 항목 | 가정 |
|---|---|
| 모델 | KoELECTRA-base급, 약 110M 파라미터 |
| 학습 데이터 | 약 50만 건 (약지도 레이블 포함) |
| 에포크 | 3 |
| 정밀도 | BF16 혼합 정밀도 (`precision="bf16-mixed"`, 통합-2 코드와 동일) |

**시간당 관점 vs 실험당 관점**

| GPU | 시간당 (가정) | 1회 학습 | **실험당 비용** | 반복 주기 |
|---|---|---|---|---|
| RTX 4090 | $0.40 | 4시간 | **$1.60** | 하루 1~2회 |
| L40S | $0.90 | 2시간 | **$1.80** | 하루 여러 회 |
| H100 | $3.00 | 1시간 | **$3.00** | 하루 여러 회 |

**여기서 강의의 역설이 제 프로젝트에서는 일어나지 않습니다.**

9-2에서 정리한 조건식을 그대로 적용해 보겠습니다.

> **총비용 배수 = 시간당 단가 배수 ÷ 학습 시간 배수**

| | 시간당 배수 | 학습 시간 배수 | 총비용 배수 | 역전? |
|---|---|---|---|---|
| **강의 사례** [강의 표] | 1.29배 | **9배** | 0.14 (7배 저렴) | ✅ 크게 역전 |
| **제 프로젝트** (4090→H100) | 7.5배 | 4배 | 1.88 (1.9배 비쌈) | ❌ 역전 안 됨 |

**왜 다른가 — 모델 크기 때문입니다.** 강의 사례는 대규모 학습이라 상위 GPU의 HBM 대역폭·FP8·Transformer 엔진이 9배 단축으로 이어집니다. 제 프로젝트의 110M 모델은 그 가속 여지가 4배 정도에 그치는데 시간당 단가는 7.5배 뛰므로, **비싼 GPU가 그냥 비싼 선택이 됩니다.**

**이것이 강의 원칙의 반례는 아닙니다.** 9-2에서 짚은 전제 — "GPU를 충분히 활용할 때만 성립한다" — 가 여기서 깨지는 것뿐입니다. 작은 모델에서는 상위 GPU의 연산 능력을 다 쓰지 못하고 데이터 로딩이 병목이 됩니다. **원칙을 외우는 것과 적용 조건을 아는 것은 다른 일**이고, 이 계산이 그 차이를 보여줍니다.

**그래서 선택 기준이 비용에서 대기 시간으로 옮겨갑니다.** 실험당 비용이 $1.60~$3.00으로 사실상 차이가 없으므로, **반복 주기가 짧은 쪽(L40S)**을 고르는 것이 합리적입니다. 강의 표의 L40S 특징란에 적힌 **"추론 특화, 비용 효율적"**이 제 워크로드와 정확히 맞습니다.

**전체 프로젝트 비용** (L40S 기준)

| 구간 | GPU시간 | 온디맨드 ($0.90/hr) | 스팟 70% 할인 ($0.27/hr) |
|---|---|---|---|
| 개발 (실험 100회 × 2h) | 200h | $180 | **$54** |
| 운영 (주 1회 × 2h × 52주) | 104h | $94 | **$28** |

스팟 전환으로 **약 $192 절감**입니다.

**스팟을 쓸 조건이 갖춰져 있는가 — 점검**

| 조건 | 상태 |
|---|---|
| 체크포인팅 자동화 | ✅ Lightning `ModelCheckpoint(save_last=True)` |
| 재개 로직 | ✅ `trainer.fit(ckpt_path="last")` |
| **체크포인트를 인스턴스 밖에 저장** | ⚠️ **별도 설정 필요.** 로컬 디스크에 두면 회수 시 함께 사라짐 |
| 회수돼도 되는 작업인가 | ✅ 개발 단계 실험은 대부분 해당 |

**결론 — 세 가지**

1. **강의의 "비싼 GPU가 더 저렴하다"는 조건부 명제입니다.** 학습 시간 단축 배수가 단가 상승 배수를 넘어야 성립하고, 그건 모델이 충분히 클 때 일어납니다. 제 프로젝트는 그 조건을 만족하지 않으므로 중간급(L40S)이 맞습니다.

2. **이 프로젝트에서 GPU 비용은 병목이 아닙니다.** 연 $82는 상담사 한 명의 하루치 인건비 수준입니다. Day 1에서 "데이터 가용성이 실제 병목"이라고 판단한 것이 숫자로 확인됩니다.

3. **그래서 최적화 대상은 돈이 아니라 반복 주기입니다.** 실험당 비용 차이가 $1.40인데 대기 시간 차이는 3시간입니다. 이 구간에서는 **금액을 비교하는 것 자체가 의미 없고, 하루에 실험을 몇 번 돌릴 수 있는가로 골라야 합니다.**

## 마무리

Day 1이 "무엇을 왜 만들 것인가"였다면 Day 2는 그 계획을 **실행 가능한 형태로 바꾸는 방법**이었습니다.

가장 크게 남은 것은 **Day 1의 추상적 원칙들이 Day 2에서 전부 구체적인 코드 한 줄로 내려앉는다는 점**입니다.

- "성공 지표를 사업 지표로 합의하라" → `ModelCheckpoint(monitor="val_recall_at_2000", mode="max")`
- "시간 분할로 평가하라" → `random_split` 대신 `created_at` 기준 분할
- "룰 300개는 관리 불가능한 부채다" → 약지도 학습의 레이블링 함수로 재활용하면 **자산**
- "당신은 구글이 아니다" → Airflow 대신 cron + 스크립트, DVC 대신 Git LFS 장부

그리고 직전 과정에서 제가 만든 붓꽃 프로젝트를 Day 2의 기준으로 점검해보니 **데이터 버전 관리 Level 0, 실험 기록 없음, 학습 환경 미고정** 상태였습니다. 잘 돌아가는 것처럼 보였던 것은 데이터가 `load_iris()`로 고정되어 있고 실험이 한 번뿐이었기 때문입니다. **"문제가 없었다"가 아니라 "문제가 드러날 조건이 아니었다"는 것** — 이것이 Day 2에서 가장 뼈아픈 확인이었습니다.
