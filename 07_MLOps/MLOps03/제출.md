### 이 프로젝트에서 실제로 잡아낸 것 3가지

1. **학습셋과 검증셋의 클래스 분포가 다르다** — `사회` 11.2% → 40.6% (+29.4%p).
   데이터 기댓값 테스트로 발견했고 `xfail(strict=True)` 로 문서화했다.
2. **Dropout 이 꺼진 채 학습되고 있었다** — HuggingFace `from_pretrained` 는 eval 모드로
   반환하고 Lightning 은 `train()` 을 강제하지 않는다. 오류 없이 조용히 과적합된다.
3. **행동 테스트가 배포 전에 결함을 찾아냈다** — Macro F1 0.6256 뒤에 IT과학 기사의 63%를
   경제로 분류하는 결함이 숨어 있었다. 평균 하나로는 안 보인다.
   현재는 `xfail` 로 표시해 **문서화만** 한 상태이고, 실제로 배포를 차단하려면
   `xfail` 마커를 떼어 수트가 빨간불이 되게 해야 한다.

## Chapter 13. ML 시스템의 테스트 전략

### 13-1. ML 테스트가 "다크 소울"이라 불리는 이유 — 전통 소프트웨어와의 3가지 차이

**① 정답의 성격이 다르다 — 통과/실패가 아니라 정도의 문제**

전통 소프트웨어는 테스트를 통과하면 "맞다"고 본다. 그러나 ML 모델은 **항상 어느 정도 틀려 있다.**
학습 중의 0이 아닌 손실(non-zero loss)은 그 자체로 "부분적인 테스트 실패"다.
따라서 ML 테스트는 "맞느냐 틀리느냐"가 아니라 **"틀린 정도가 허용 범위 안이냐"** 를 판단한다.

실제로 이 레포의 성능 게이트(`tests/test_performance.py::test_beats_baseline`)도
`assert f1 == 1.0` 이 아니라 `assert 모델 F1 - 베이스라인 F1 >= 0.01` 형태의 임계값 비교다.
"얼마나 틀려도 되는가"를 숫자로 정해 둔 것이다.

**② 결정론적이지 않다**

전통 소프트웨어는 같은 입력에 항상 같은 출력을 낸다. ML은 부동소수점 오차, 데이터 셔플,
비결정적 커널 때문에 같은 환경에서도 결과가 미세하게 달라진다.
그래서 값의 정확한 일치가 아니라 **통계적 분포가 허용 범위 안인지**를 본다.

이 레포는 `pl.seed_everything(42, workers=True)` 로 재현성을 최대한 확보했지만,
그럼에도 행동 테스트는 확률값을 정확히 비교하지 않고 `argmax` 의 일치나
`p > 0.30` 같은 느슨한 범위로 검사한다.

**③ 동작을 결정하는 것이 코드만이 아니다 — 데이터가 코드의 일부다**

전통 소프트웨어는 코드를 안 바꾸면 동작이 안 바뀐다. ML 시스템의 동작은
**코드 + 데이터 + 하이퍼파라미터**의 함수라, 코드를 한 줄도 안 고쳐도 데이터 소스가
바뀌면 모델이 조용히 다른 것을 학습한다. 그래서 코드 테스트만으로는 부족하고
**데이터 기댓값 테스트**가 별도로 필요하다.

이 프로젝트에서 실제로 겪었다. KLUE YNAT 은 학습셋과 검증셋의 클래스 분포가 다르다
(`사회` 11.2% → 40.6%, +29.4%p). 코드에는 아무 문제가 없는데 검증 점수만 낮게 나온다.
`tests/test_data.py` 가 없었다면 "모델이 나쁘다"고 오진했을 것이다.

### 13-2. 테스트 수트를 "분류기"로 볼 때 오탐이 위험한 이유

테스트 수트는 "이 커밋에 버그가 있는가?"를 판정하는 분류기이고,
**탐지(Detection)와 오탐(False Alarm)은 트레이드오프** 관계다.

오탐이 위험한 이유는 실패가 사람의 행동을 바꾸기 때문이다.
오탐이 반복되면 개발자는 **코드가 아니라 테스트를 고쳐서 통과시키기 시작한다.**
그 순간 테스트는 안전망이 아니라 형식적인 절차가 되고, 진짜 버그가 섞여 들어와도
"또 그 테스트네" 하고 넘어가게 된다.

**이 프로젝트에서 실제로 마주친 사례 — 하마터면 오탐 공장을 만들 뻔했다**

학습/검증 분포가 다르다는 것을 발견하고 이런 테스트를 만들었다.

```python
def test_train_val_distribution_similar(ynat):
    assert worst_gap <= 0.10  # 클래스 비율 차이 10%p 이내
```

이 테스트는 **영원히 실패한다.** KLUE YNAT 데이터셋 자체의 성질이라 고칠 수가 없다.
그대로 두면 매 실행마다 빨간불이 뜨고, 결국 이 테스트를 지우거나 임계값을
0.30 으로 올려 무력화하게 된다 — 전형적인 오탐 처리 실패다.

그래서 `@pytest.mark.xfail(strict=True)` 로 바꿨다.

- 실패가 **예상된 상태**로 관리되어 수트는 초록불을 유지한다
- 실패 사유가 코드에 문서로 남는다
- 데이터 소스가 교체되어 이 가정이 참이 되면 **XPASS** 로 알려준다

또 하나. 제목 길이 테스트의 경계를 실측값(최소 4자, 최대 44자)에 딱 맞춰
`assert 4 <= len <= 44` 로 잡을 뻔했다. 이러면 데이터가 조금만 갱신돼도 오탐이 난다.
"제목이 1자일 리 없고 500자를 넘을 리 없다" 수준의 **느슨한 경계**로 두었다.

### 13-3. 암기 테스트가 실패했을 때 의심할 원인 5가지와 디버깅 방법

`overfit_batches=1` 로 배치 하나조차 외우지 못한다면, 성능 문제가 아니라 **버그**다.

| # | 원인 (강의 13.5) | 디버깅 방법 |
|---|---|---|
| 1 | **그래디언트 계산 오류** — `backward()` 는 돌지만 특정 층에 그래디언트가 전파되지 않음. `requires_grad=False` 이거나 연산 그래프가 끊긴 경우 | `named_parameters()` 를 돌며 `p.grad` 가 None 이거나 전부 0 인 층을 찾는다 |
| 2 | **데이터 셔플링 오류** — x 와 y 의 순서가 어긋나 정답을 맞출 수가 없음. 놀랍도록 흔하다 | 배치 하나를 꺼내 `tokenizer.decode(input_ids)` 로 원문을 복원하고 레이블과 눈으로 대조 |
| 3 | **전처리 버그** — 정규화 값이 잘못됨(평균을 빼야 하는데 더하는 등) | 전처리 전후 텐서의 통계(평균·표준편차·범위)를 찍어 기대값과 비교. 토크나이저라면 `decode` 로 왕복 확인 |
| 4 | **수치적 문제** — 그래디언트 폭주/소실로 NaN·Inf 발생 | `torch.isfinite()` 로 손실과 로짓을 검사. 그래디언트 노름을 로깅해 스파이크를 본다. `gradient_clip_val` 을 걸고 재실행 |
| 5 | **옵티마이저 설정 오류** — 학습률이 0 이거나 잘못된 파라미터 그룹이 전달됨 | 스텝 전후로 파라미터 값이 실제로 변하는지 비교. `optimizer.param_groups` 의 `lr` 과 파라미터 수를 확인 |

> **덧붙임 — 이 프로젝트에서 실제로 겪은 6번째 원인**
> 위 5가지에 없지만 **LR 스케줄러가 학습률을 떨어뜨려** 암기가 안 되는 경우를 만났다.
> `OneCycleLR` 이 학습률을 어닐링하면서 30에포크 안에 손실이 0.19 까지밖에 안 내려갔다.
> 5번(옵티마이저 설정)의 변형으로 볼 수 있다. 암기 테스트에서는 규제뿐 아니라
> **스케줄러도 꺼야 한다**(`use_scheduler=False`).

**이 레포에 구현한 것**

- 원인 2 → `tests/test_model.py::test_gradients_reach_backbone`
  임베딩 층에 그래디언트가 실제로 도달하는지 확인한다.
- 원인 4 → `tests/test_training.py::_disable_dropout`
  암기 테스트 전에 모든 `nn.Dropout` 의 `p` 를 0 으로 만든다.
- 원인 5 → `tests/test_model.py::test_loss_decreases_on_single_batch`
  8스텝 안에 손실이 내려가는지 본다. 암기 테스트의 축소판이라 몇 초면 끝나 PR 단계에 넣을 수 있다.

**이 프로젝트에서 만난, 위 5가지에 없는 종류의 버그 — 본 학습에서 Dropout 이 꺼져 있었다.**

메커니즘은 이렇다.

1. `nn.Module.__init__` 이 LightningModule 을 `training=True` 로 만든다
2. `from_pretrained()` 가 반환한 모델은 **이미 eval 모드**다
3. 그걸 `self.model = ...` 로 대입해도 **부모의 모드가 전파되지 않는다**
4. Lightning 은 `fit` 시작 시 경고만 하고 `.train()` 을 호출하지 않아 불일치가 유지된다

실제로 `on_train_start` 훅만 뺀 모델로 `fit` 을 돌려 `training_step` 안을 계측했다.

```
훅 없음:  LightningModule.training=True   backbone.training=False   Dropout 38개 전부 비활성
훅 있음:  LightningModule.training=True   backbone.training=True    Dropout 38개 전부 활성
```

`self.training` 은 True 인데 하위 모듈은 False 다. 모드 플래그는 모듈마다 따로 있고,
`.train()` 을 호출해야 재귀적으로 맞춰진다.

이 버그는 **암기 테스트로는 잡히지 않는다.** Dropout 이 꺼지면 암기는 오히려 잘 되기 때문이다.
Lightning 이 낸 `Found 232 module(s) in eval mode` 경고를 그냥 넘겼다면 계속 몰랐을 것이고,
조용히 과적합된 모델을 배포했을 것이다. 회귀 테스트는
`tests/test_model.py::test_backbone_is_in_train_mode_after_hook` 에 있다.
`on_train_start` 에서 `self.model.train()` 을 호출해 고쳤다. 자세한 기록은
[docs/실행기록.md](docs/실행기록.md#3-트러블슈팅-기록) 에 있다.

### 13-4. 데이터 기댓값 테스트의 "느슨한 경계" 원칙

**원칙**: 경계는 "물리적·논리적으로 불가능한 값"을 막는 선에서 잡는다.
"정상적으로 있을 법한 범위"로 잡으면 안 된다.

**엄격하게 잡으면 생기는 문제**

1. **오탐** — 정상 데이터인데 실패한다. 사람 키를 4~8피트로 잡으면 어린이 데이터가 들어오는 순간 실패한다.
2. **테스트 신뢰 붕괴** — 위 13-2 의 악순환. 오탐이 반복되면 테스트를 고쳐 통과시키게 된다.
3. **유지보수 비용** — 데이터가 갱신될 때마다 경계를 다시 맞춰야 한다.

키 예시라면 "음수일 수 없고 30피트를 넘을 수 없다" 정도가 적절하다.
30피트짜리 사람은 없으므로 이 테스트가 실패했다면 **확실히 데이터가 잘못된 것**이다.

**이 레포의 적용** (`tests/test_data.py`)

| 테스트 | 실측값 | 설정한 경계 | 여유 |
|---|---|---|---|
| 제목 길이 | 4 ~ 44자 | **2 ~ 500자** | 넉넉 |
| 레이블 범위 | 0 ~ 6 | **0 ~ 6** | 없음 (논리적 상한이라 여유가 필요 없다) |
| 최소 클래스 비율 | 11.2% | **3% 이상** | 3.7배 |
| 학습 데이터 수 | 45,678 | **1,000 이상** | 넉넉 |

레이블 범위만 딱 맞춘 이유는, 이건 통계값이 아니라 **분류 헤드의 크기와 반드시 일치해야 하는
논리적 제약**이기 때문이다. 7 클래스 모델에 레이블 7이 들어오면 무조건 오류다.
느슨한 경계 원칙은 "관측된 통계값"에 적용하는 것이지, 구조적 불변식에는 적용하지 않는다.

### 13-5. 불변성 테스트 vs 방향성 테스트 — 내 프로젝트 적용 예시

| | 불변성(Invariance) | 방향성(Directional) |
|---|---|---|
| 정의 | 의미를 **바꾸지 않는** 변형에는 예측이 **그대로**여야 함 | 의미를 **바꾸는** 변형에는 예측이 **정해진 방향**으로 움직여야 함 |
| 검사 대상 | 모델이 무관한 표면적 특징에 반응하지 않는가 | 모델이 핵심 신호를 실제로 사용하는가 |

**불변성 테스트** (`tests/test_behavior.py::test_invariance_to_punctuation_and_spacing`)

```
"삼성전자 새 반도체 공장 착공"  vs  "삼성전자, 새 반도체 공장 착공"   (쉼표 유무)
"미국 대선 후보 TV토론 개최"    vs  "미국 대선 후보 TV 토론 개최"     (띄어쓰기)
"프로야구 한국시리즈 7차전 돌입" vs "프로야구 한국시리즈 7 차전 돌입"  (숫자 띄어쓰기)
```

쉼표 하나로 카테고리가 바뀌면 그 모델은 서비스에 올릴 수 없다. 뉴스 제목은 매체마다
표기 규칙이 달라서, 이 불변성이 깨지면 특정 언론사 기사만 계속 오분류된다.

**방향성 테스트** (`tests/test_behavior.py::test_directional_topic_swap`)

```
"삼성전자 반도체 신기술 공개"          → 스포츠 확률 p1
"대한민국 올림픽 축구 대표팀 명단 공개" → 스포츠 확률 p2
assert p2 > p1
```

문형("~ 공개")은 유지하고 주제어만 바꿨다. 스포츠 확률이 올라가지 않으면
모델이 주제어가 아니라 문형이나 길이 같은 엉뚱한 신호를 보고 있다는 뜻이다.

정확한 클래스를 요구하지 않고 **확률의 상대적 변화**만 본 이유는, 절대 클래스를 요구하면
모델이 조금만 달라져도 깨지는 취약한 테스트가 되기 때문이다(13-2 의 오탐 문제).

## Chapter 14. 모델 트러블슈팅 3단계

### 14-1. 왜 "Fast"가 "Right"보다 먼저인가

**성능은 실험 반복 횟수의 함수이고, 반복 횟수는 실험 1회 소요 시간의 역수이기 때문이다.**

하루에 1번 실험하는 팀과 10번 실험하는 팀 사이에는 넘을 수 없는 생산성 차이가 있다.
"Right"(성능 끌어올리기)는 본질적으로 탐색 과정이라 시도 횟수가 곧 도달 가능한 성능의
상한을 정한다. 느린 상태로 "Right"를 시작하면, 좋은 아이디어가 있어도 검증할 기회가 없다.

**이 프로젝트의 실측**

| 시점 | 설정 | 배치당 | 8,000건 1에포크 | 하루에 가능한 실험 |
|---|---|---|---|---|
| 최초 계획 | `klue/bert-base`, `max_length=64` 고정 패딩 | 22.75s | **약 95분** | 사실상 1~2회 |
| 모델 교체 | `koelectra-small`, 고정 패딩 | 약 1.75~1.79s | 7.3~7.6분 | 10회 남짓 |
| **+ 동적 패딩** | `koelectra-small`, 동적 패딩 | **0.74s** | **3.1분** | **수십 회** |

최초 계획대로였다면 3에포크에 5시간이 걸려 하이퍼파라미터를 바꿔볼 엄두를 못 냈을 것이다.
속도를 30배 줄이고 나서야 "학습률을 바꿔보자", "에포크를 늘려보자"가 실행 가능한 선택지가 됐다.

### 14-2. OOM 해결 4단계와 Adam 메모리

**4단계 (순서대로)**

1. **정밀도 낮추기** — `precision="16-mixed"`. 메모리 거의 절반, 속도도 향상되는 "공짜 점심"이라 가장 먼저.
2. **배치 사이즈 줄이기** — 가장 직관적. 다만 너무 작으면 학습이 불안정해진다.
3. **그래디언트 축적** — `accumulate_grad_batches=4`. 물리 배치는 작게, 수학적으로는 4배 큰 배치 효과. 2단계의 부작용(불안정)을 보상한다.
4. **그래디언트 체크포인팅** — 순전파 중간 활성값을 저장하지 않고 역전파 때 재계산. **메모리를 속도와 맞바꾼다.** 속도 손해가 있어 마지막.

순서의 논리는 **손해가 적은 것부터**다. 1번은 손해가 거의 없고, 4번은 속도를 확실히 잃는다.

**Adam 이 파라미터의 3~4배 메모리를 쓰는 이유**

Adam 은 각 파라미터마다 두 개의 상태를 파라미터와 **같은 크기로** 유지한다.

| 항목 | 크기 |
|---|---|
| 파라미터 자체 | 1× |
| 그래디언트 | 1× |
| 1차 모멘텀 `m` (그래디언트 지수이동평균) | 1× |
| 2차 모멘텀 `v` (그래디언트 제곱의 지수이동평균) | 1× |
| **합계** | **약 4×** |

그래서 모델이 GPU 메모리의 1/4도 안 되는데 OOM 이 나면 옵티마이저를 의심해야 한다.
SGD 는 모멘텀 상태가 하나뿐(또는 없음)이라 훨씬 적게 쓴다.

### 14-3. 프로파일링 결과별 대응

**`get_train_batch` 가 60%인 경우 — 데이터 굶주림**

GPU 가 CPU 를 기다리고 있다. 모델을 아무리 빠르게 해도 암달의 법칙에 따라
전체 향상은 40% 가 상한이다. 효과가 큰 순서로:

1. `num_workers` 증가 (CPU 코어 수의 절반~전체 사이에서 실험)
2. `persistent_workers=True` — 에포크마다 워커를 재생성하지 않는다
3. `pin_memory=True` — CPU→GPU 전송을 비동기로
4. **무거운 전처리 사전 캐싱** — 토크나이징을 학습 루프에서 빼서 `.arrow` 로 저장
5. 데이터를 NVMe SSD 로, GPU 기반 전처리(DALI) 검토

**`training_step` 이 90%인 경우 — 모델 연산이 병목**

데이터 파이프라인을 아무리 손봐도 10% 밖에 못 줄인다. 모델 쪽을 봐야 한다:

1. 혼합 정밀도 `precision="16-mixed"`
2. `torch.compile(model)` — 커널 퓨전으로 20~50%
3. **입력 크기 줄이기** — 시퀀스 길이는 연산량에 직접 영향을 준다
4. 모델 경량화 (더 작은 백본, 레이어 프루닝)
5. 배치 크기를 키워 GPU 활용률 향상

**내 프로젝트의 실측 결과**

`Trainer(profiler="simple")` 로 측정했다 (`reports/profile.txt`).

| 구간 | 비중 |
|---|---|
| `optimizer_step` (순전파+역전파 포함) | 74.6% |
| ├ `training_step` | 31.9% |
| └ `backward` | 31.0% |
| `NewsDataModule.setup` (1회성 토크나이징) | 16.8% |
| **`train_dataloader_next` (배치 공급)** | **0.48%** |

**데이터 로딩은 병목이 아니다.** 토크나이징을 `.map()` 으로 학습 전에 끝내두었고
(위 데이터 굶주림 대책 4번을 이미 적용한 셈), 그래서 `num_workers` 를 늘려봐야 의미가 없다.
Windows 라 `num_workers=0` 인데도 문제가 안 되는 이유가 이것이다.

병목이 모델 연산이므로 **입력 크기를 줄이는 쪽**(위 3번)을 택했다.
토큰 길이가 평균 15.7 인데 64 로 고정 패딩하던 것을 배치별 동적 패딩으로 바꿔
시퀀스 길이 64 → 22, 배치당 1.75초 → 0.74초가 됐다.

### 14-4. 스케일링 법칙 — 흐름과 비즈니스 가치

**흐름을 내 말로**

성능(손실)은 연산량·데이터 크기·파라미터 수에 대해 **거듭제곱 법칙**을 따른다.
로그-로그 축에서 직선이 되므로, 감당 가능한 작은 실험 몇 개만 돌려도
큰 실험의 결과를 **직선을 연장해서** 미리 알 수 있다.

1. 작은 실험 3~5개 — 자원을 단계적으로 늘리며 각각의 최종 손실을 기록
2. 로그-로그 차트에 점을 찍고 직선 회귀
3. 목표 손실선까지 직선을 연장 → 필요한 데이터·GPU 시간을 숫자로 얻는다

**비즈니스적 가치**

"GPU 를 5배 더 쓰면 성능이 얼마나 오르나?"에 **투자 결정 전에** 숫자로 답할 수 있다.
- 3개월 튜닝 대신 데이터를 늘리는 게 낫다는 판단을 근거를 갖고 내릴 수 있다
- "이 목표는 현재 예산으로 도달 불가"를 미리 알아 프로젝트를 재정의할 수 있다
- 반대로 "여기서 멈춰도 된다"는 정지 조건이 생긴다

Chinchilla 의 교훈도 같은 맥락이다. 파라미터만 키우고 데이터를 그대로 두면
비용 대비 효율이 나쁘다 — **균형 있게** 늘려야 한다.

**내 프로젝트에서 한 것 — 스케일링 법칙이 아니라 "데이터 규모 민감도 예비 관찰"**

정식 스케일링 법칙은 위 3단계(작은 실험 3~5개 → 로그-로그 회귀 → 외삽)를 요구한다.
아래는 **점이 2개뿐이라 회귀도 외삽도 할 수 없다.** 기울기를 말할 수 없고,
"데이터를 더 넣으면 성능이 오른다"는 방향만 확인한 수준이다.
또한 손실이 아니라 Macro F1 을, 트랜스포머가 아니라 TF-IDF 를 잰 것이라
본 모델의 스케일링을 대변하지도 않는다.

| 학습 데이터 | Macro F1 |
|---|---|
| 8,000건 | 0.5836 |
| 45,678건 (5.7배) | 0.6957 |

데이터를 5.7배 늘려 F1 이 +0.112 올랐다. 이것으로 알 수 있는 것은
**"CPU 제약으로 8,000건만 쓰면 최소한 이 정도 손해를 본다"** 는 하한선 하나뿐이다.

제대로 하려면 트랜스포머로 학습 규모를 2,000 / 4,000 / 8,000 / 16,000 / 45,678 처럼
4~5단계로 나눠 각각의 검증 손실을 기록하고, 로그-로그 축에서 회귀한 뒤 외삽해야 한다.
CPU 로는 마지막 두 점만으로도 몇 시간이 걸려 이번 범위에서 하지 못했다. **다음 과제다.**

### 14-5. 성능 저하 진단 — 내 최근 프로젝트 분석

진단의 첫 걸음은 언제나 **train_loss 와 val_loss 의 비교**다.

| 상황 | 증상 | 처방 |
|---|---|---|
| 오버피팅 | train 손실 낮음, val 손실 높음 | 데이터 늘리기, 규제 강화, 모델 축소 |
| 언더피팅 | train 손실도 높음 | 모델 키우기, 학습 더, 규제 완화 |
| 분포 변화 | train/val 은 괜찮은데 실제 데이터에서 나쁨 | 둘 다 — 데이터 재수집 + 재학습 |

**사례 A — 붓꽃 MLOps 프로젝트 (직전 과정): 오버피팅, 그리고 그것을 못 보던 게이트**

RandomForest 로 학습하고 **같은 데이터로 채점**하고 있었다. 정확도가 1.0 에 가깝게 나와
"성능 좋다"고 판단했는데, 이건 오버피팅 여부를 볼 수 없는 구조였다.

홀드아웃 20% 를 분리하고 다시 재니 이렇게 나왔다.

```
학습 데이터 채점  ≈ 1.00     ← 게이트가 보던 값 (의미 없음)
5-fold 교차검증     0.9583
홀드아웃            0.9333    ← 한 번도 안 본 데이터
```

`1.00 → 0.9333` 의 간격이 오버피팅의 크기다. 붓꽃은 데이터가 단순해 실害가 작지만,
**문제는 성능이 아니라 성능을 측정하는 방식이 틀렸다는 것**이었다.
처방은 규제 강화가 아니라 **평가 설계 수정**이었다.

**사례 B — 이번 뉴스 분류 프로젝트: 분포 변화**

KLUE YNAT 은 학습셋과 검증셋의 클래스 분포가 다르다(`사회` 11.2% → 40.6%).
train/val 손실 비교만으로는 오버피팅처럼 보이지만 실제 원인은 분포 차이다.

처방은 진단표대로 "데이터 재수집 + 재학습"이지만, 공개 데이터셋이라 재수집이 불가능하다.
대신 이렇게 대응했다.

1. Accuracy 대신 **Macro F1** — 다수 클래스(`사회`)에 점수가 끌려가지 않게
2. 검증 점수의 **절대값을 신뢰하지 않는다** — 같은 부분집합으로 잰 베이스라인과의 **상대 비교**로 판단
3. 분포 차이를 `xfail` 테스트로 **명시적으로 문서화** — 나중에 이 데이터를 쓰는 사람이 같은 함정에 빠지지 않게

## Chapter 15. LLM 시대의 평가와 모니터링

### 15-1. Accuracy 만으로 LLM 을 평가할 수 없는 이유와 추가 평가 차원

**이유**: LLM 의 출력은 정답이 하나로 정해지지 않는 **생성물**이다.
같은 질문에 대해 옳은 답이 여러 개일 수 있고, 표현이 달라도 맞을 수 있다.
게다가 "정확하지만 딱딱한 답변"과 "자연스럽지만 환각이 섞인 답변" 중 무엇이 나은지는
비즈니스 맥락에 따라 다르다. 이 모든 것을 하나의 숫자로 요약하면
**어느 차원이 약한지 알 수 없어 개선 방향을 못 잡는다.**

**추가로 필요한 평가 차원 5가지**

| 차원 | 묻는 것 |
|---|---|
| **사실성 / 환각 (Faithfulness)** | 답변 내용이 근거 문서에 실제로 있는가, 지어냈는가 |
| **유창성 (Fluency)** | 한국어로 자연스럽게 읽히는가 |
| **근거 참조 (Attribution)** | RAG 에서 어떤 문서를 근거로 삼았는지 정확히 가리키는가 |
| **의도 이해 (Intent Understanding)** | 사용자가 진짜 묻는 것을 파악했는가 |
| **안전성 (Safety)** | 유해하거나 편향된 내용을 포함하지 않는가 |

여기에 **톤/스타일**(브랜드 목소리에 맞는가)까지 더하면 6개다.

---

### 15-2. LLM-as-a-Judge 의 장점, 한계, 편향 완화

**장점**
- 인간 평가보다 **10~100배 빠르고 저렴**하다 → 매 커밋마다 평가를 돌릴 수 있다
- 인간 평가와의 **상관관계가 0.7~0.9** 로 높다
- 평가 기준을 프롬프트로 정의하므로 기준 변경이 쉽고 기록에 남는다

**한계 — 평가자 자신의 편향**
- **길이 편향**: 긴 답변에 더 높은 점수를 주는 경향
- **자기 선호 편향**: 자기와 같은 계열 모델이 쓴 답변을 선호
- **위치 편향**: 두 답변을 비교시키면 앞에 놓인 것을 선호
- **문체 편향**: 자신감 있는 어투를 정확성으로 오인

**완화 방법 (하나를 고르라면 — 위치 스왑 + 평균)**

두 답변을 비교 평가할 때 **A/B 순서를 뒤집어 두 번 평가하고 점수를 평균**낸다.
두 번의 결론이 다르면 그 케이스는 "판정 불가"로 분류해 인간 평가로 넘긴다.
위치 편향을 직접 상쇄하면서, 판정이 불안정한 케이스를 자동으로 골라내는 이득도 있다.

추가로 병행할 것:
- 평가 프롬프트에 **"길이에 관계없이 핵심만 평가하라"** 를 명시 (길이 편향)
- 주 1회 또는 모델 업데이트 시 **50~100개 샘플의 인간 평가**로 Judge 를 교정(calibration)
- 채점 대상과 **다른 계열의 모델**을 Judge 로 사용 (자기 선호 편향)

### 15-3. 드리프트 3유형과 내 프로젝트에서 가장 가능성 높은 유형

| 유형 | 한 문장 정의 |
|---|---|
| **입력 드리프트** | 모델에 들어오는 데이터의 통계적 분포가 학습 시점과 달라지는 것 |
| **출력 드리프트** | 모델이 내놓는 예측의 분포가 달라지는 것 (특정 클래스를 과도하게 예측하기 시작) |
| **성능 드리프트** | 실제 정답과 비교한 성능 자체가 시간에 따라 떨어지는 것 (가장 확실하지만 정답 확보에 시간이 걸림) |

**내 프로젝트(뉴스 분류)에서 가장 가능성 높은 유형: 입력 드리프트**

뉴스는 세상의 사건을 그대로 반영하므로 입력 분포가 계속 움직인다.

- **어휘 드리프트**: 학습 시점에 없던 고유명사가 계속 생긴다(새 기업명, 신조어, 신기술). 토크나이저가 이를 잘게 쪼개면서 표현력이 떨어진다.
- **주제 비중 변화**: 선거철에는 `정치`, 올림픽 기간에는 `스포츠` 기사가 급증한다. Spotify 의 크리스마스 사례처럼 **예측 가능한 계절성**이다.
- **카테고리 경계 이동**: "AI 반도체 수출 규제"는 `IT과학`인가 `경제`인가 `세계`인가. 산업 구조가 바뀌면 정답 자체가 흔들린다 — 이건 개념 드리프트에 가깝다.

**주의 — 이미 발견한 분포 차이는 입력 드리프트가 아니다.**
학습셋과 검증셋의 `사회` 비율 차이(11.2% → 40.6%)는 **레이블 분포 변화(label shift / prior shift)**,
즉 `P(y)` 가 달라진 것이다. 입력 드리프트는 `P(x)` — 실제 입력 피처의 통계 분포가 변하는 것이다.
둘은 원인도 대응도 다르다. 레이블 분포 변화는 **로짓 보정이나 클래스 가중치**로 재학습 없이도
완화할 수 있지만, 입력 드리프트는 대개 **재수집·재학습**이 필요하다.
이 프로젝트에는 배포 전부터 레이블 분포 변화가 있고, 배포 후에는 입력 드리프트가 예상된다.

**모니터링 계획**: 자료형에 따라 검정을 나눈다. KS 검정은 연속형 분포용이라
범주형에 그대로 쓰면 안 된다.

| 감시 대상 | 자료형 | 검정 | 드리프트 유형 |
|---|---|---|---|
| 제목 토큰 길이 | 연속형 | **KS 검정** | 입력 |
| 미등록 토큰(UNK) 비율 | 연속형(비율) | **KS 검정** | 입력 |
| 예측 클래스 분포 | 범주형 | **카이제곱 적합도 / JS divergence** | 출력 |
| 예측 최대 확률(confidence) | 연속형 | **KS 검정** | 출력 |

학습 시점 기준과 매일 비교하고, 임계값을 3일 연속 넘으면 알림.
성능 드리프트는 편집자의 카테고리 수정 이력이 정답 역할을 할 수 있어,
그 데이터가 쌓이면 직접 추적한다.

### 15-4. "모델은 시간이 지나면 썩는다" — 코로나19 사례와 필요한 시스템

**의미**: 전통 소프트웨어는 코드를 안 바꾸면 계속 같게 동작한다. ML 모델은
**코드를 한 줄도 안 바꿔도 바깥 세상이 변하면 성능이 떨어진다.**
모델은 과거 데이터로 만든 세상의 스냅샷이고, 세상은 계속 움직이기 때문이다.

**코로나19 사례**

2020년 초를 기점으로 소비자 행동이 급격히 바뀌었다.

- 수요 예측 모델: 마스크·손소독제 수요가 하루아침에 폭증. 과거 어떤 계절성으로도 설명 안 됨
- 추천 시스템: 여행·외식 추천이 무의미해지고 홈트레이닝·배달 수요가 폭증
- 신용 평가 모델: 소득 안정성 패턴이 통째로 달라짐

**코드는 그대로였는데 모델만 쓸모없어졌다.** 게다가 이건 서서히 오는 드리프트가 아니라
**급격한 단절**이라, 점진적 재학습으로는 따라갈 수 없었다.

**필요한 시스템 4가지**

1. **드리프트 감지** — 입력 피처와 예측 분포를 학습 시점 기준과 상시 비교 (KS 검정, KL 발산). Evidently AI, WhyLabs 같은 도구나 직접 구축.
2. **자동 알림** — 사람이 대시보드를 열어봐야 아는 구조면 늦는다. 임계값을 넘으면 Slack/이메일로 자동 발송.
3. **재학습 파이프라인** — 감지에서 배포까지가 자동이어야 한다. Uber 는 예측 분포가 유의미하게 변하면 재학습이 자동 트리거된다. **직전 과정에서 만든 CI/CD 가 정확히 이 조각이다.** 푸시 한 번에 학습→테스트→빌드→배포가 도는 파이프라인이 있으면, 트리거를 "푸시"에서 "드리프트 알림"으로 바꾸기만 하면 된다.
4. **롤백 경로** — 새 모델이 더 나쁠 수 있다. 붓꽃 프로젝트에서 이미지에 `:latest` 와 함께 **커밋 해시 태그**를 붙인 이유가 이것이다. 어느 코드가 돌고 있는지 특정되어야 되돌릴 수 있다.

**중요한 단서**: 드리프트 알림이 울리면 먼저 **"진짜 세상이 변한 것인가, 우리 파이프라인이
깨진 것인가"** 를 구분해야 한다. 데이터 소스 API 가 바뀌어 필드명이 달라진 경우도
드리프트처럼 보이지만, 그건 재학습이 아니라 코드 수정이 필요한 상황이다.
갑작스러운 변화일수록 파이프라인 버그일 확률이 높다.

### 통합-3. 병목 예측과 검증 — 그리고 예측이 틀렸다

**측정 전 가설**: "토크나이징과 데이터 로딩이 병목일 것이다."
근거는 Windows 라 `num_workers=0` 으로 강제되고, Lightning 이 직접 경고까지 냈기 때문이다.

```
The 'train_dataloader' does not have many workers which may be a bottleneck.
Consider increasing the value of the `num_workers` argument to `num_workers=7`
```

**검증 계획**: `Trainer(profiler="simple")` 로 1에포크를 돌려 `get_train_batch` 와
`training_step` 의 비중을 비교한다.

**결과 — 가설이 틀렸다.**

```
train_dataloader_next   0.48%     ← 데이터 로딩
training_step          31.87%
backward               31.02%     ← 모델 연산이 63%
```

`.map()` 으로 토크나이징을 학습 전에 끝내둔 덕에 배치 공급은 사실상 공짜였다.
Lightning 의 경고는 **일반적인 조언이지 이 프로젝트의 진단이 아니었다.**
경고만 믿고 `num_workers` 를 올렸다면 Windows 멀티프로세싱 오류만 얻고 속도는 그대로였을 것이다.

**한 번 더 틀렸다.** 프로파일링 전에는 벽시계 시간을 스텝 수로 나눠 "6.7초/스텝"이라고
판단했는데, 실제는 0.8초였다. 프로세스 시작·데이터셋 로드·토크나이징이 전부 분자에 섞여 있었고,
CSV 로거가 버퍼링해서 파일 수정 시각이 실제 진행보다 늦었다.

**교훈**: Ch14.2.1 의 "직감에 반하는 딥러닝 성능"과 "추측이 아니라 측정으로"를
두 번 다 어기고서야 배웠다. 병목 판단에는 **프로파일러의 숫자**만 쓴다.
