# Chapter 0. Introduction

### 0-1. 모델 배포 / Full Stack DL / MLOps는 각각 어떤 범위를 담당하며, 왜 세 과정이 분리되어야 하는가

| 과정 | 담당 범위 | 한 문장 |
|---|---|---|
| 모델 배포 개론 | 완성된 모델 → 사용자 인터페이스. FastAPI 엔드포인트, Streamlit 데모 | **"어떻게 전달하는가"** |
| Full Stack DL | 모델의 생애 전체. 올바른 문제인가, 데이터는 신뢰할 수 있는가, 실험은 재현되는가, 성능 저하의 원인을 추적할 수 있는가 | **"무엇을 왜 만드는가"** |
| MLOps | 그 사고방식의 인프라 구현. Docker, GCP, Airflow, CI/CD | **"어떻게 지속 가능하게 만드는가"** |

**분리되어야 하는 이유는 순서에 있습니다.**

배포를 먼저 경험해야 그 다음 질문이 실감납니다. 직전 과정에서 붓꽃 분류 모델을 Docker 이미지로 만들어 GCP VM에 올리고 외부 IP로 접속되는 것까지 확인했는데, 성공한 직후에 바로 든 생각이 "그래서 이제 이걸 어떻게 유지하지"였습니다. 데이터가 바뀌면? 성능이 떨어지면 어떻게 알지? 모델을 새로 학습하면 어떤 게 더 나은지 어떻게 비교하지? FSDL은 정확히 그 질문들의 목록입니다. 배포 경험이 없는 상태에서 이 내용을 들으면 추상적인 훈계로만 들립니다.

반대로 MLOps가 먼저 오면 안 되는 이유는 Chapter 6.7이 경고하는 **도구 페티시즘**입니다. 풀어야 할 문제를 모르는 상태에서 Airflow와 Feature Store부터 배우면, 필요 없는 파이프라인을 짓는 데 프로젝트 초기 에너지를 전부 소진합니다.

정리하면 **배포는 "할 수 있다"를, FSDL은 "무엇을 왜"를, MLOps는 "지속 가능하게"를** 담당합니다. 가운데가 빠지면 잘 굴러가는 파이프라인으로 틀린 문제를 풀게 됩니다.

### 0-2. "평평한 지구 ML"과 "둥근 지구 ML"의 차이 (30초 설명) / 데이터 플라이휠은 어디에 해당하는가

**30초 설명:**

> 학교에서 배운 ML은 직선입니다. 데이터 모으고 → 학습하고 → 평가하고 → 배포하면 끝. 성능이 좋으면 프로젝트가 끝난 겁니다. 이게 평평한 지구예요.
>
> 그런데 실제로는 배포가 끝이 아니라 **출발선**입니다. 사용자가 쓰기 시작하면 새로운 데이터가 생기고, 그 데이터로 모델을 고치고, 좋아진 모델이 사용자를 더 끌어오고, 그럼 데이터가 더 쌓입니다. 계속 제자리로 돌아옵니다. 지구가 둥글어서요.
>
> 차이는 한 줄입니다. **평평한 지구에서는 배포가 종료 조건이고, 둥근 지구에서는 배포가 시작 조건입니다.**

**데이터 플라이휠의 위치:** 둥근 지구의 **외부 루프(Outer Loop) 그 자체**입니다. 배포 → 사용 → 데이터 축적 → 모델 개선 → 사용자 증가 → 데이터 증가로 이어지는 순환이 플라이휠이고, 이 순환이 존재한다는 사실이 곧 지구가 둥글다는 뜻입니다. 평평한 지구 모델에는 이 루프가 아예 그려져 있지 않습니다.

### 0-3. ML Powered Product와 MLOps의 지향점 차이를 구체적 질문 하나씩으로

**MLOps의 질문:**
> "모델 v2를 무중단으로 배포하고, 실사용 성능이 기준치 아래로 떨어지면 자동으로 v1으로 롤백하려면 파이프라인을 어떻게 구성해야 하는가?"

**ML Powered Product의 질문:**
> "사기 탐지 결과를 사용자에게 '거래 차단'으로 보여줄 것인가, '주의 필요' 배지로 보여줄 것인가? 그리고 그 선택이 우리가 앞으로 얻게 될 레이블의 양과 질을 어떻게 바꾸는가?"

**차이의 본질:** MLOps는 **시스템 내부**를 향하고, ML Powered Product는 **사용자와 조직**을 향합니다.

주목할 점은 두 번째 질문이 첫 번째보다 **먼저** 와야 한다는 것입니다. 차단으로 하면 사용자는 그 게시글을 볼 수 없고, 그러면 "사용자가 이 게시글을 보고도 거래했는가"라는 신호를 영영 얻지 못합니다. UI 결정 하나가 데이터 수집 구조를 결정하고, 데이터 수집 구조가 앞으로 만들 수 있는 모델의 상한을 정합니다. 인프라를 아무리 잘 만들어도 이 결정을 되돌릴 수는 없습니다.

# Chapter 1. ML 제품의 가치와 현대 ML 생태계

### 1-1. Software 1.0과 2.0의 근본적 차이 / 왜 전혀 다른 개발·테스트·운영 전략이 필요한가

**근본적 차이는 "동작이 어디에 저장되는가"입니다.**

- **Software 1.0**: 사람이 입력과 출력의 관계를 명시적으로 작성합니다. 동작이 **코드**에 있습니다.
- **Software 2.0**: 사람은 데이터와 목적 함수만 정의하고, 관계는 경사하강법이 찾아냅니다. 동작이 **가중치**에 있고, 그 가중치는 **데이터**에서 왔습니다.

이 차이가 세 가지 전략을 전부 바꿉니다.

**개발 전략** — 1.0은 스펙을 정하고 구현합니다. 2.0은 데이터를 확보하는 것이 곧 개발입니다. 코드 100줄을 잘 쓰는 것보다 레이블 1만 건을 제대로 모으는 것이 본 작업이고, 그래서 "엔지니어가 데이터 작업을 한다"는 것이 잡일이 아니라 핵심 업무가 됩니다.

**테스트 전략** — 1.0은 입력 분기를 열거할 수 있어서 단위 테스트가 성립합니다. 2.0은 입력 공간이 연속이고 사실상 무한해서 열거가 불가능합니다. 그래서 "이 입력에 이 출력"이 아니라 **분포 단위의 평가**, 사용자 세그먼트별 슬라이스 성능, 과거 실패 케이스를 모은 회귀 테스트셋 같은 다른 도구가 필요합니다.

**운영 전략** — 1.0은 코드를 안 고치면 어제와 오늘의 동작이 같습니다. 2.0은 **코드가 그대로여도 입력 분포가 변하면 동작이 변합니다.** 배포 후 모니터링이 있으면 좋은 것이 아니라 없으면 안 되는 이유가 여기 있습니다. 제 프로젝트처럼 상대가 능동적으로 회피하는 환경에서는 이 성질이 특히 치명적입니다.

### 1-2. CACE 현상이 전통 소프트웨어에서는 왜 덜 문제가 되고, ML 시스템에서는 왜 치명적인가

**전통 소프트웨어에서 덜 문제가 되는 이유는 경계가 인터페이스로 강제되기 때문입니다.**

A 모듈을 고쳐도 B 모듈은 계약(시그니처, 사전·사후 조건)만 지켜지면 영향을 받지 않습니다. 이 경계 덕분에 세 가지가 가능합니다. 모듈 단위 테스트가 성립하고, 문제가 생기면 이진 탐색으로 원인 범위를 좁힐 수 있고, 문제가 된 커밋만 되돌리면 됩니다.

**ML에서 치명적인 이유는 그 경계가 아예 없기 때문입니다.**

모든 입력 피처가 하나의 가중치 덩어리 안에서 섞입니다. 피처 하나를 제거하면 남은 피처들의 가중치가 전부 재배치됩니다. "이 부분만 테스트"라는 개념이 성립하지 않고, 이상이 생겼을 때 어느 변경 때문인지 격리할 수단이 없습니다.

실질적인 위험은 **영향 범위를 사전에 예측할 수 없다**는 점입니다. 안전해 보이는 변경 — 예를 들어 판매자 프로필 데이터의 크롤링 소스를 하나 교체하는 일 — 이 전혀 관계없어 보이는 카테고리의 탐지 성능을 무너뜨릴 수 있습니다.

되돌리는 비용도 다릅니다. 롤백 단위가 코드가 아니라 **(코드 + 데이터 스냅샷 + 학습된 가중치)** 세트이고, 이 셋을 짝지어 버전 관리하지 않았다면 되돌리는 것 자체가 불가능합니다.

### 1-3. "기술의 범용화"가 ML 엔지니어의 역할을 어떻게 변화시키고 있는가

**2018년의 희소 자원은 "모델을 만들 수 있는 능력"이었습니다.** 논문을 재현하고, 아키텍처를 설계하고, 학습을 수렴시키는 일 자체가 진입장벽이었고 그 장벽이 곧 경쟁력이었습니다.

**2026년에는 그 능력이 더 이상 희소하지 않습니다.** `transformers` 몇 줄, API 호출 한 번으로 최첨단 성능에 접근할 수 있습니다. 모델을 만드는 능력만으로는 차별화되지 않습니다.

**희소성은 다음 네 곳으로 이동했습니다.**

1. **무엇을 만들지 고르는 능력** — 실현 가능성과 임팩트를 판단해 착수 여부를 결정하는 일. 기술이 쉬워질수록 "할 수 있는 것"이 많아지고, 그럴수록 "해야 하는 것"을 고르는 판단의 가치가 올라갑니다.
2. **데이터를 확보하고 관리하는 능력** — 모델은 복제되지만 데이터는 복제되지 않습니다. 제 프로젝트에서 진짜 자산은 모델이 아니라 상담사들이 쌓아온 판단 이력입니다.
3. **평가를 설계하는 능력** — LLM 기반 시스템은 정확도 하나로 측정되지 않습니다. 무엇을 좋다고 볼 것인지 정의하는 일 자체가 전문 역량이 되었습니다.
4. **시스템으로 통합하고 운영하는 능력** — 모델 하나가 아니라 룰·모델·사람이 얽힌 전체가 제품입니다.

**한 문장으로:** 희소성이 *"모델을 만들 수 있는가"*에서 *"이 문제에 ML이 맞는지 판단하고, 데이터 루프를 설계하고, 결과를 신뢰할 수 있게 검증하는가"*로 옮겨갔습니다.

# Chapter 2. ML 도입 여부 결정과 우선순위 설정

### 2-1. 프로젝트를 실현 가능성 × 임팩트 매트릭스에 배치하면 어느 사분면인가

**결론: 실현 가능성 高 × 임팩트 高 — 최우선 착수 사분면**

**실현 가능성이 높은 근거**

| 판단 기준 | 평가 |
|---|---|
| 유사 논문·벤치마크 존재 | 스팸 탐지, 이상거래탐지(FDS), 텍스트 분류 연구가 풍부 |
| 양질의 데이터 확보 | 사내에 신고 이력과 상담사 처리 결과가 이미 축적됨 — 콜드 스타트 아님 |
| 요구 정확도의 현실성 | 자동 차단이 아니라 검토 큐 라우팅이므로 재현율 위주로 낮게 설정 가능 |
| 기존 휴리스틱 존재 | 룰 300개가 이미 운영 중 → **비교 대상은 명확하나, 실제 성능 베이스라인은 별도 측정 필요** (6-1 참조) |

**임팩트가 높은 근거**

사기 피해액은 직접적인 금전 손실인 동시에 플랫폼 신뢰도와 직결됩니다. 신고 기반(평균 3일 지연) 대응을 등록 시점 탐지로 앞당기면 피해 **건수 자체**가 줄어듭니다. 이미 발생한 피해를 처리하는 것과 발생을 막는 것은 사업 지표에서 전혀 다른 크기입니다.

**다만 한 가지 유보**

임팩트가 크다는 것은 **잘못 조치했을 때의 비용도 크다**는 뜻입니다. 만약 모델 판단만으로 게시글을 자동 차단한다면, 부당하게 차단된 정상 판매자는 항의 없이 조용히 떠날 수 있고 그 손실은 로그에도 남지 않습니다. 그래서 이 프로젝트는 사분면상 최우선이더라도 **아키타입을 Human-in-the-loop으로 잡아 오탐의 영향이 사용자에게 직접 닿지 않게 해야** 성립합니다. 매트릭스 배치가 착수 여부를 정하고, 아키타입 선택이 그 착수를 안전하게 만듭니다.

### 2-2. "API로 충분한가?"에 답하려면 구체적으로 무엇을 확인해야 하는가

여섯 가지를 순서대로 확인합니다.

**1. 성능** — 실제 사기 게시글 500건 + 정상 500건으로 프롬프팅만 해서 재현율과 정밀도를 측정합니다. 기준은 절대 수치가 아니라 **기존 룰 베이스라인을 넘는가**입니다.

**2. 지연시간** — 게시글 등록 플로우에 동기로 태울 것인지가 먼저입니다. 동기라면 API 왕복 지연(모델과 프롬프트 길이에 따라 다르지만 대략 1~3초로 가정)을 사용자가 기다려야 하는데 이건 어렵습니다. **비동기로 뺄 수 있으면 이 제약은 사라집니다** — 요구사항을 확인하기 전에 아키텍처로 제약을 없앨 수 있는지 먼저 봅니다.

**3. 비용** — 일 30만 건 × 토큰 단가. 건당 0.001달러로 가정하면 **일 300달러, 월 약 9,000달러**입니다. 이 정도 규모면 자체 모델 서빙(GPU 인스턴스 + 운영 인력) 쪽이 유리해지므로, 비용만 놓고 보면 **API를 최종 서빙 수단으로 쓰기는 어렵다**는 결론이 먼저 보입니다. API는 PoC와 레이블 부트스트랩 용도로 한정하고 본 서빙은 자체 모델로 가는 경로가 유력합니다.

**4. 데이터 보안과 규제** — 게시글에는 연락처, 계좌번호 같은 개인정보가 포함됩니다. 외부 API로 전송할 법적 근거가 개인정보 처리방침에 있는지, 없다면 마스킹으로 해결 가능한지 확인합니다. **이 항목이 걸리면 앞의 세 개가 아무리 좋아도 끝입니다.**

**5. 도메인 특수성** — 우리 플랫폼에서만 통하는 사기 은어나 카테고리별 패턴을 프롬프트로 주입할 수 있는지, 아니면 학습이 필요한지 봅니다.

**6. 적대적 적응 속도** — 사기 수법이 바뀔 때 프롬프트 수정으로 따라갈 수 있는지, 재학습이 필요한지. 대응 주기가 곧 운영 비용입니다.

**실무적 결론의 형태:** 1~2번이 통과하면 일단 API로 PoC를 돌리고, 3~4번이 걸리면 자체 모델로 갑니다. 현실에서 가장 흔한 경로는 **"API로 PoC 및 레이블 자동 생성 → 레이블이 쌓이면 소형 모델 파인튜닝으로 이관"**입니다. API를 최종 답이 아니라 부트스트랩 도구로 쓰는 방식입니다.

### 2-3. ML 도입 전에 시도해야 할 4가지 대안과 각각이 더 적합한 상황

**1. 규칙 기반(Rule-based)** — 결정적 신호가 소수일 때.

> 예: "선입금만 받습니다" 문구 + 가입 7일 이내 + 시세 50% 이하, 이 세 조건의 AND만으로도 악질 사기의 상당수가 걸립니다. 유지보수 비용이 낮고, 왜 걸렸는지 상담사에게 설명할 수 있습니다.

**2. Human-in-the-loop** — 오판 비용이 극단적으로 클 때.

> 예: 계정 영구 정지처럼 되돌리기 어려운 조치는 모델 점수와 무관하게 사람이 최종 결정합니다. 이건 ML을 안 쓰는 것이 아니라 **ML의 권한을 제한하는** 선택입니다.

**3. Foundation Model API** — 자연어 이해가 핵심이고 도메인 특수성이 낮을 때.

> 예: 게시글 본문에서 "카톡으로 연락 주세요" 같은 외부 메신저 유도 문구를 뽑아내는 일은 학습 없이 프롬프트만으로 즉시 됩니다.

**4. 전통 통계 기법** — 신호가 수치이고 해석 가능성이 필요할 때.

> 예: 판매자별 게시글 등록 간격의 이상치는 z-score로 충분합니다. 정규분포 가정 하에서 왜 이상인지 상담사에게 숫자로 설명할 수 있고, 이 설명 가능성이 실무에서는 정확도 몇 %보다 중요합니다.

**공통 원칙:** 네 가지 모두 **ML보다 싸고 빠르고 설명 가능합니다.** ML은 이것들로 안 되는 부분에만 투입하는 것이 맞습니다. 제 프로젝트도 전량 대체가 아니라 명백한 건은 룰에 남기고 **애매한 구간만 모델에 넘기는 하이브리드**가 현실적입니다.

# Chapter 3. ML 프로젝트 라이프사이클

### 3-1. 라이프사이클 4단계와 각 단계의 핵심 활동

| 단계 | 핵심 활동 (한 문장) |
|---|---|
| **1. 기획 및 설정** | 이 문제를 ML로 풀지 결정하고, 성공 지표·예산·윤리 기준을 확정한다 |
| **2. 데이터 수집 및 레이블링** | 학습 데이터를 모으고 레이블 품질과 가이드라인을 관리한다 |
| **3. 모델 학습 및 디버깅** | 베이스라인부터 시작해 모델을 개선하고 실험을 기록·비교한다 |
| **4. 배포 및 모니터링** | 파일럿으로 내보내고 실사용 성능과 사용자 피드백을 관측한다 |

네 단계는 순서도처럼 보이지만 실제로는 끊임없이 이전 단계로 되돌아갑니다. **되돌아감을 없애는 것이 목표가 아니라, 되돌아갈 때의 비용이 낮도록 각 단계를 가볍게 설계하는 것이 목표입니다.**

### 3-2. "4단계 → 2단계 되돌아감"이 가장 흔한 이유 / 기획 단계에서 던져야 할 질문

**흔한 이유는 두 가지가 겹치기 때문입니다.**

첫째, **오프라인 평가셋은 과거의 데이터**입니다. 실제 트래픽에는 학습 데이터에 없던 유형이 계속 들어옵니다.

둘째, **모델을 배포하는 행위 자체가 입력 분포를 바꿉니다.** 제 프로젝트에서는 이게 특히 두드러집니다. 사기 탐지는 상대가 있는 게임이라, 배포하는 순간 사기꾼이 우리 모델을 상대로 학습하기 시작합니다. 우리가 잘 막을수록 상대는 더 빨리 변합니다. 이 되돌아감은 사고가 아니라 **필연**입니다.

**기획 단계에서 던져야 할 질문 네 가지**

1. **"평가셋이 실제 트래픽 분포를 대표하는가? 랜덤 분할이 아니라 시간 기준으로 나눴는가?"**
   랜덤 분할은 미래 데이터를 학습에 섞어 성능을 과대평가합니다. 드리프트가 있는 도메인에서는 반드시 시간 분할이어야 합니다.

2. **"모델이 틀린 케이스를 어떻게 자동으로 수집해 레이블링 큐에 넣을 것인가?"**
   실패 수집 경로를 배포 전에 설계해야 합니다. 나중에 붙이려면 이미 지나간 실패는 복구할 수 없습니다.

3. **"입력 분포가 변했다는 것을 성능 지표가 아니라 무엇으로 먼저 알아챌 것인가?"**
   성능 지표는 정답 레이블이 확정된 뒤에야 계산되므로 항상 늦습니다. 더 빠른 선행 지표가 필요합니다.

4. **"재학습 1회에 드는 시간과 비용은? 주 1회가 가능한 구조인가?"**
   되돌아감이 필연이라면, 되돌아가는 비용이 프로젝트의 실질 제약입니다.

### 3-3. 플라이휠이 자연스럽게 형성되는 제품 vs 인위적으로 설계해야 하는 제품

**자연스럽게 형성되는 제품** — 사용자의 정상적인 행동이 그 자체로 정답 신호인 경우.

- **추천 시스템**: 클릭, 스킵, 시청 완료가 곧 선호 레이블입니다. 사용자는 레이블링을 하고 있다는 의식조차 없습니다.
- **검색**: 어떤 결과를 클릭했는지가 관련도 레이블입니다.
- **제 프로젝트**도 여기에 가깝습니다. 구매자의 신고, 상담사의 검토 결과, 거래 분쟁 접수가 전부 별도 노동 없이 레이블이 됩니다.

**인위적 설계가 필요한 제품** — 정답을 사용자가 모르거나, 알아도 알려줄 이유가 없는 경우.

- **의료 영상 판독 보조**: 환자는 정답을 모르고, 확진까지 몇 주가 걸립니다. 판독의의 최종 소견을 시스템에 남기도록 워크플로우에 강제로 끼워 넣어야 레이블이 생깁니다.
- **이탈 예측**: 예측이 맞았는지는 몇 달 뒤에야 알 수 있고, 이탈할 것 같아서 쿠폰을 줬다면 결과가 바뀌어버려 **원래 어땠을지(반사실)를 관측할 수 없습니다.**

**차이의 본질은 두 가지입니다.**

1. **레이블 획득에 사용자의 추가 노동이 필요한가**
2. **정답이 얼마나 빨리 관측되는가**

둘 다 나쁘면 플라이휠은 저절로 돌지 않고, UI와 업무 프로세스 안에 레이블 수집 장치를 의도적으로 심어야 합니다. 제 프로젝트에서도 신고는 자연스럽지만 **"신고되지 않은 게시글이 정말 정상인가"**는 관측되지 않으므로, 이 부분만큼은 인위적 설계(무작위 표본 강제 검토)가 필요합니다.

# Chapter 4. ML 제품의 3가지 아키타입

### 4-1. 세 아키타입에 해당하는 실제 서비스

| 아키타입 | 서비스 | 설명 |
|---|---|---|
| **Software 2.0** | 유튜브 추천 | 조회수·최신순 룰로 하던 정렬을 개인화 모델로 대체 |
| **Human-in-the-loop** | GitHub Copilot | 코드를 제안하고 개발자가 수락·수정·거절. 최종 결정은 사람 |
| **Autonomous** | Waymo 로보택시 | 운전석에 사람이 없고 시스템이 최종 결정 |

### 4-2. Human-in-the-loop → Autonomous 진화 경로와 전환 조건

제 프로젝트를 기준으로 그리면 다음과 같습니다. **단계별 기간과 동의율 수치는 PoC에서 검증할 목표치로 가정한 값**입니다.

**1단계 (0~3개월, 가정) — 전량 HITL**
모델은 위험도 점수만 매기고, 고위험 큐를 상담사가 전부 검토합니다. 자동 조치는 없습니다. 이 단계의 목적은 성능 측정이 아니라 **레이블 축적**과 **상담사 판단 기준의 명문화**입니다. 사람이 무엇을 근거로 판단하는지 사유 코드로 남겨야 다음 단계가 가능합니다.

**2단계 (3~6개월, 가정) — 신뢰도 구간 분기**
위험도 상위 구간에서 상담사 동의율이 목표치(가정: 98%)를 넘는 것이 확인되면, **그 구간만** "자동 노출 제한 + 사후 검토"로 전환합니다. 조치가 걸린 뒤에도 사람이 되돌릴 수 있습니다.

**3단계 (6~12개월, 가정) — 부분 자율**
되돌림 비율이 충분히 낮게 유지되면 자동 조치의 범위를 넓힙니다. 단 **계정 영구 정지처럼 되돌리기 어려운 조치는 끝까지 HITL로 남깁니다.**

**전환 조건 네 가지**

1. 해당 신뢰도 구간에서 상담사 동의율이 목표치를 **통계적으로 유의하게** 넘을 것 (충분한 표본 확보가 전제)
2. 오탐 시 **되돌리는 경로가 존재**하고 그 비용이 낮을 것
3. 오탐이 **특정 사용자 집단에 쏠리지 않을 것** (공정성 검증)
4. 자동 조치 후에도 **사후 샘플링 검토를 계속할 것** — 자율화는 감시 중단이 아님

**핵심:** 전환의 단위는 "모델 전체"가 아니라 **"신뢰도 구간 × 조치 강도"**입니다. 되돌리기 쉬운 약한 조치부터 자동화하고, 강한 조치는 마지막까지 사람이 쥐고 있습니다.

### 4-3. 내 프로젝트의 아키타입과 그에 따른 정확도·실패 비용·플라이휠 전략

**아키타입: Human-in-the-loop** (장기적으로 고신뢰 구간만 부분 Autonomous)

**정확도 요구사항**

자동 차단이 아니므로 정밀도보다 **재현율이 우선**입니다. 더 정확히 말하면, 상담사 처리 용량이 일 2,000건으로 고정되어 있으므로 실질 지표는 **Recall@2000** — "상위 2,000건 안에 실제 사기의 몇 %가 들어오는가"입니다. 전체 AUC가 아무리 좋아도 상위 구간에 사기가 안 몰리면 의미가 없습니다. **제약 조건이 지표의 형태를 결정합니다.**

**실패 비용**

| 실패 유형 | 결과 | 비용 |
|---|---|---|
| 미탐 (FN) | 사기 피해 발생 | 금전 손실 + 플랫폼 신뢰도 하락. **큼** |
| 오탐 (FP) | 정상 게시글이 검토 큐에 들어감 | HITL이라 사용자에게 보이지 않음. **상담사 시간으로 한정** |

**이것이 HITL을 선택한 이유입니다.** 자동 차단 아키타입이었다면 FP 비용이 "정상 판매자의 이탈"로 폭증합니다. 아키타입 선택 하나로 실패 비용의 크기를 통제한 셈입니다.

**플라이휠 전략**

- 상담사의 검토 결과(사기 확정/정상)가 **고품질 레이블**이 됩니다. 이것이 플라이휠의 주 엔진입니다.
- 검토 UI에 **사유 코드를 필수 입력**으로 넣어, 단순 이진 레이블 이상의 신호를 축적합니다. 나중에 "어떤 유형의 사기가 늘고 있는가"를 분석할 수 있는 유일한 자산이 됩니다.
- 모델이 저위험으로 분류했는데 나중에 신고가 들어온 건은 **False Negative(FN, 미탐) 사례**입니다. 실제로는 사기(Positive)인데 모델이 정상(Negative)으로 판정한 경우이므로, 따로 모아 우선 학습에 투입합니다.

# Chapter 5. ML 프로젝트 팀 구성과 조직 설계

### 5-1. ML 프로젝트에 필요한 5가지 역할 / 풀스택 ML 엔지니어는 어디까지 커버 가능한가

**5가지 역할**

| 역할 | 담당 |
|---|---|
| ML 엔지니어 / Applied Scientist | 모델 선택·학습·최적화, 데이터 파이프라인과 서빙까지 |
| 데이터 엔지니어 | 데이터 수집·정제·파이프라인 구축 |
| ML Platform 엔지니어 | 실험 관리, 모델 레지스트리, 배포 인프라 |
| 프로덕트 매니저 | ML의 가능성과 한계를 이해하고 사용자 가치와 기술을 연결 |
| 도메인 전문가 | 데이터 의미 해석, 레이블링 가이드라인 설계, 결과 타당성 검증 |

**풀스택 ML 엔지니어의 커버 범위**

- **확실히 커버**: ML 엔지니어 전부 + 데이터 엔지니어의 소규모 버전 + Platform의 최소 구성(실험 기록, 컨테이너 배포). 직전 과정에서 학습 → FastAPI → Docker → Docker Hub → GCP 배포까지 혼자 3일 만에 돌려봤고, 실제로 가능합니다.

- **부분 커버**: PM 역할 중 "기술적 실현 가능성 판단"은 가능하지만, **"사용자 가치 정의와 우선순위 협상"은 조직 권한의 문제**라 개인 역량으로 대체되지 않습니다.

- **커버 불가**: **도메인 전문가.** 사기 게시글의 은어나 최신 수법은 매일 그것을 보는 상담팀만 압니다. 이건 사람 수의 문제가 아니라 **지식의 소재지** 문제라 풀스택으로 흡수되지 않습니다. 오히려 풀스택 엔지니어일수록 "내가 데이터를 이해했다"고 착각하기 쉬워 위험합니다.

- **규모의 벽**: 팀이 커지고 데이터가 TB급이 되면 Platform 역할은 전임이 필요해집니다. **풀스택은 PoC~초기 프로덕션 구간의 개념이지 영구적 조직 구조가 아닙니다.**

### 5-2. "리서치와 프로덕션의 거리를 좁혀라"는 원칙이 팀의 일하는 방식에 요구하는 변화

**1. 산출물의 정의가 바뀝니다.**
리서치의 완료 조건이 "노트북 + 정확도 숫자"에서 **"돌아가는 데모 링크"**로 바뀝니다. 실제로 붓꽃 모델도 정확도만 확인하고 끝냈다면, 컨테이너 안에서 scikit-learn 버전이 달라 joblib 로드가 흔들리는 문제를 몰랐을 겁니다. 배포까지 가봐야 드러나는 문제가 있습니다.

**2. 모델 개발자가 배포 제약을 처음부터 압니다.**
지연시간, 메모리, 의존성 버전이 실험 설계 단계의 입력이 됩니다. e2-micro의 1GB 메모리에 컨테이너 두 개를 올리려고 swap을 계산해야 했던 것처럼, **제약이 나중에 통보되는 것이 아니라 처음부터 조건**이 됩니다. 나중에 알면 모델을 처음부터 다시 만들어야 합니다.

**3. 인수인계 회의가 줄고 공유 환경이 늘어납니다.**
"리서치가 만들고 엔지니어링이 받는다"는 단계가 존재하면 그 경계에서 반드시 재현 실패가 발생합니다. 양쪽이 **같은 Docker 이미지**를 쓰면 인수인계라는 행위 자체가 사라집니다. 이것이 다음 과정에서 배울 컨테이너화의 진짜 이유입니다.

**4. 이해관계자 커뮤니케이션이 바뀝니다.**
표 대신 링크를 보냅니다. 비개발자가 직접 슬라이더를 움직여 보면 "이 정도면 되겠다/안 되겠다"는 조직 합의가 훨씬 빨리 납니다. Chapter 2가 지적한 실패 원인 중 **"조직 내 공감대 부족"을 정면으로 겨냥하는 실천**입니다.

# Chapter 6. ML 프로젝트 기획의 실전 체크리스트

### 6-1. 필수 질문 10가지 중 가장 답하기 어려운 3개와 그 이유

**① 3번 — 베이스라인: "ML 없이 달성할 수 있는 최선의 성능은?"**

어려운 이유: **기존 룰 300개의 성능이 측정된 적이 없습니다.** 룰에 걸린 건만 로그가 남고, 걸리지 않은 건은 기록이 없어서 재현율의 분모를 구할 수 없습니다. 베이스라인을 세우려면 정답셋 구축이 선행되어야 하는데, 그 작업 자체가 프로젝트만큼 큽니다. **"베이스라인을 모른다"는 것은 개선 여부를 판정할 수 없다는 뜻**이라 이 항목이 가장 시급합니다.

**② 5번 — 라벨: "정답 데이터를 어떻게 얻을 것인가, 비용은?"**

어려운 이유: **사기의 정답은 시간이 지나야 확정됩니다.** 신고가 들어오지 않은 게시글이 정말 정상인지, 피해자가 신고를 포기한 것인지 구분할 방법이 없습니다. 즉 우리 레이블은 구조적으로 **미탐이 정상으로 오염**되어 있습니다. PU-learning처럼 다루거나 표본을 뽑아 사후 조사를 해야 하는데 둘 다 비용이 듭니다.

**③ 7번 — 실패 비용: "모델이 틀렸을 때의 비용은?"**

어려운 이유: FN 비용(피해액)은 금액으로 계산되지만, **FP 비용은 단계에 따라 성격이 달라지고 뒤로 갈수록 관측이 어려워집니다.**

- **현재의 HITL 단계**: FP 비용은 상담사의 검토 시간과 **검토 큐의 기회비용**입니다. 정상 게시글이 일 2,000건의 처리 용량을 차지하면 그만큼 실제 사기 게시글을 못 봅니다. 이건 측정 가능합니다.
- **향후 자동 노출 제한 단계**: 여기서부터 정상 판매자의 불편과 이탈 비용이 추가되는데, **부당하게 제한된 판매자가 항의 없이 떠나면 로그에 아무것도 남지 않습니다.** 관측이 불가능한 쪽은 이 부분입니다.

비용의 한쪽 면만 보고 임계값을 정하면 재현율만 올리는 방향으로 계속 편향됩니다.

**세 항목의 공통점**

셋 다 **"관측되지 않는 것을 어떻게 다룰 것인가"**의 문제입니다. 기획 단계에서 이를 인지하지 못하면, 나중에 **ML 지표는 좋아지는데 사업 지표는 개선되지 않는** 상황을 만나고 원인도 찾지 못합니다.

### 6-2. 4가지 멘탈 모델을 내 도메인에 적용

**① 예측 비용의 하락**

현재는 신고가 들어온 건만 상담사가 봅니다. 만약 전문 상담사를 무한히 고용해 하루 30만 건을 전부 즉시 검토할 수 있다면? **피해가 발생하기 전에 차단됩니다.** 그 가치가 ML이 노릴 지점입니다. 그리고 실제로 예측 비용이 크게 낮아졌습니다. LLM API로 전량 스코어링하면 일 300달러 수준이지만(2-2 참조), 레이블을 쌓아 소형 분류 모델로 이관하면 그보다 훨씬 낮아집니다. 몇 년 전이라면 어느 쪽이든 경제성이 없었을 활용처입니다.

**② 마찰 감소**

지금 구매자는 스스로 판매자 프로필을 확인하고 시세를 비교하며 위험을 판단해야 합니다. 이 인지 부담을 **"주의 필요" 배지 하나**로 덜어줍니다. 다만 마찰은 양방향으로 봐야 합니다 — 정상 판매자가 부당하게 제한받는 것도 마찰이므로, 한쪽 마찰을 줄이려다 다른 쪽을 늘리지 않는지 함께 측정해야 합니다.

**③ Software 2.0 — 수동 규칙의 대체**

룰 300개는 이미 사람이 관리할 수 없는 수준입니다. 룰끼리 충돌하고, 추가한 사람이 퇴사해서 왜 존재하는지 모르는 룰이 있습니다. 전형적인 ML 전환 후보입니다. 다만 **전량 대체가 아니라, 명백한 룰은 남기고 애매한 구간만 모델에 넘기는 하이브리드**가 현실적입니다. 설명 가능성이 필요한 조치는 룰이 여전히 유리합니다.

**④ 업계 벤치마킹**

당근마켓·번개장터의 기술 블로그, 금융권 FDS 도입 사례, Stripe Radar 같은 결제 사기 탐지 제품의 공개 자료를 봅니다. 특히 주목할 것은 **그들이 어떤 지표로 성과를 발표하는가**입니다. 정확도가 아니라 "피해 신고 건수 X% 감소"처럼 **사업 지표로 말하는 사례**가 우리 성공 지표 설계의 직접적인 참고가 됩니다.

### 6-3. "정확도에 9를 하나 더하면 비용 10배" 법칙의 의미 / 요구 정확도를 낮추는 제품 설계

**내 프로젝트에서의 의미**

다행히 **극단적 정확도가 필요 없는 구조**입니다. HITL이라 모델이 틀려도 상담사가 잡습니다. 99.9%가 아니라 "상위 2,000건 안에 사기의 70%"만 들어와도, 신고 기반 사후 대응인 현행 대비 명백한 개선입니다.

**만약 자동 차단으로 갔다면** 정상 판매자를 차단하는 순간 CS 인입과 이탈이 발생하므로 **훨씬 높은 정밀도가 요구되고, 목표 정확도를 올릴수록 비용은 비선형적으로 증가합니다.** 구체적으로 몇 %가 필요한지는 실험 전에 단정할 수 없고, 강의에서 언급된 "9를 하나 더할 때 비용 약 10배"도 어디까지나 매우 거친 가이드라인입니다.

> **아키타입 선택이 곧 정확도 요구사항 선택이고, 정확도 요구사항이 곧 예산입니다.**
> 세 가지는 따로 결정되는 것이 아니라 하나의 결정입니다.

**요구 정확도를 낮추는 제품 설계 방법 네 가지**

1. **조치 강도를 낮춘다** — 차단 대신 "주의" 배지, 배지 대신 검토 큐 라우팅. 조치가 약할수록 허용 오차가 커집니다.
2. **되돌릴 수 있게 만든다** — 즉시 이의제기 버튼을 두면 FP 비용이 "영구 손실"에서 "일시적 불편"으로 바뀝니다.
3. **모델이 기권할 수 있게 한다** — 신뢰도가 낮으면 판단하지 않고 사람에게 넘깁니다. 모델은 **자신 있는 구간에서만** 정확하면 됩니다.
4. **문제를 다시 쪼갠다** — "사기인가?"를 직접 맞히는 대신 "선입금 요구 문구가 있는가?"처럼 객관적이고 쉬운 하위 문제로 분해하고, 종합 판단은 사람이 합니다.

네 가지 모두 **모델을 개선하는 것이 아니라 제품을 바꿔서 요구 정확도 자체를 내리는** 접근입니다. 대개 이쪽이 훨씬 쌉니다.

### 6-4. "당신은 구글이 아니다" — 지금 필요한 도구와 나중에 도입해도 되는 도구

**지금 당장 필요한 것**

- **정답셋과 평가 스크립트** — 없으면 무엇을 해도 개선 여부를 알 수 없습니다. 최우선.
- **노트북 + 룰 베이스라인 재현** — 비교 대상이 있어야 합니다.
- **실험 결과를 남길 최소 장치** — 스프레드시트로 충분합니다.
- **상담사 검토 결과를 저장하는 테이블** — 플라이휠의 시작점.

**나중에 도입해도 되는 것**

| 도구 | 필요해지는 시점 |
|---|---|
| Feature Store | 모델이 여러 개가 되어 피처 재사용 문제가 생길 때 |
| Airflow 자동 재학습 | 수동 재학습 주기가 병목이 될 때 (초기엔 주 1회 수동으로 충분) |
| 모델 레지스트리 / A/B 테스트 | 비교할 모델이 2개 이상 동시 운영될 때 |
| Kubernetes | 트래픽이 단일 인스턴스를 넘을 때 |

**판단 기준:** **"이 도구가 없어서 지금 무엇이 막혔는가?"**에 구체적으로 답할 수 있을 때만 도입합니다. 답이 "나중에 필요할 것 같아서"라면 아직입니다.

**단 하나의 예외**

**데이터 수집 경로만은 처음부터 만듭니다.** 인프라는 나중에 얹을 수 있지만, **쌓지 않은 과거 데이터는 소급해서 만들 수 없습니다.** 상담사 검토 결과 테이블을 초기에 안 만들면 6개월 뒤 학습 데이터가 없습니다. 이것만은 "나중에"가 통하지 않습니다.

# Day 1 통합 체크포인트

### 통합-1. 오늘 다룬 내용이 왜 모델 배포 직후이자 MLOps 직전에 위치해야 하는가

**모델 배포 직후여야 하는 이유**

FSDL의 질문들 — "정말 올바른 문제를 풀고 있는가", "배포 후 성능이 떨어지면 어떻게 아는가" — 은 **배포를 해본 사람에게만 실감납니다.** 직전 과정에서 붓꽃 API를 GCP에 올려 외부 IP로 접속되는 것까지 확인하고 나니, 성공한 그 자리에서 바로 "이제 이걸 어떻게 유지하지, 데이터가 바뀌면 어쩌지"라는 질문이 생겼습니다. FSDL은 정확히 그 질문들의 목록입니다. 배포 경험 없이 들었다면 추상적인 훈계로만 들렸을 내용입니다.

**MLOps 직전이어야 하는 이유**

Docker, Airflow, CI/CD는 **풀어야 할 문제를 알고 나서** 배워야 도구 페티시즘에 빠지지 않습니다. 순서가 뒤집혀 인프라를 먼저 배우면, 해결할 문제가 없는데 파이프라인부터 짓게 됩니다. Chapter 6.7이 경고하는 바로 그 함정입니다.

**한 줄 요약**

> 배포는 **"할 수 있다"**, FSDL은 **"무엇을 왜"**, MLOps는 **"지속 가능하게"**.
> 가운데가 빠지면 잘 굴러가는 파이프라인으로 틀린 문제를 풀게 됩니다.

### 통합-2. 종합 기획 — 6단계 프레임워크 적용

**(1) ML이 정말 필요한가?**
**예. 단, 전량은 아닙니다.** 명백한 패턴은 룰이 더 싸고 설명 가능합니다. **룰로는 안 걸리는데 상담사는 의심하는 애매한 구간** — 그곳이 ML의 영역입니다.

**(2) Build vs Buy vs API?**
**API로 PoC, 자체 모델로 이관.** 초기에는 LLM API로 게시글의 위험 신호를 뽑아 레이블링 속도를 올리고, 레이블이 쌓이면 소형 분류 모델을 파인튜닝해 **비용·지연시간·개인정보 문제를 한 번에** 해결합니다.

**(3) 아키타입은?**
**Human-in-the-loop.** 고신뢰 구간의 약한 조치부터 점진적으로 자율화합니다.

**(4) 실현 가능성 × 임팩트?**
**高 × 高 — 최우선 착수.** 사내 데이터 보유, 유사 연구 풍부, 피해액이라는 명확한 사업 지표.

**(5) 비용의 3대 동인?**

| 동인 | 평가 |
|---|---|
| 데이터 가용성 | 사내 이력이 있어 콜드 스타트는 아니지만, **레이블이 미탐으로 오염**되어 있음. 정제가 실제 병목 |
| 정확도 요구사항 | HITL이라 요구 수준이 낮음. **여기서 가장 크게 절약** |
| 문제 난이도 | 일반 텍스트 분류는 엔지니어링이지만 **적대적 적응**이 있어 연구 성격이 섞임. 불확실성 예산 필요 |

**(6) PoC 종료 조건?**
- 룰 베이스라인 대비 Recall@2000이 유의미하게 높은가
- 상담사 10명 × 2주 검토로 확보한 정답셋이 본 개발을 지탱할 만한가
- 일 30만 건 스코어링이 예산 안에 들어오는가

하나라도 "아니오"면 중단이 아니라 **범위를 좁힙니다** — 예를 들어 전 카테고리가 아니라 피해가 집중된 3개 카테고리만.

### 통합-3. 둥근 지구 설계 — 데이터 플라이휠 구체화

**사용자 행동 → 데이터**

| 행동 | 얻는 신호 |
|---|---|
| 구매자의 **신고** | 명시적 양성 레이블 |
| 상담사의 **검토 결과 + 사유 코드** | 고품질 레이블 — **플라이휠의 주 엔진** |
| 거래 **분쟁/환불 접수** | 지연된 양성 신호 |
| 게시글의 **정상 거래 완료** | 약한 음성 신호 |
| "주의" 배지를 보고도 **거래를 진행했는지** | UI 효과 측정 신호 |

**데이터 → 모델 개선**

- 모델이 저위험으로 봤는데 신고된 건 = **False Negative(FN, 미탐) 사례.** 주 단위로 모아 우선 학습에 투입.
- 상담사가 모델과 다르게 판단한 건 = **불일치 케이스.** 가이드라인 개정 또는 학습 데이터 보강 대상.

**모델 → 더 많은 사용자**

사기 피해 감소 → 플랫폼 신뢰도 상승 → 거래량 증가 → 게시글·신고·검토 데이터 증가 → 다시 모델 개선.

**초기 구현 수준**

"당신은 구글이 아니다" 원칙대로, **상담사 검토 결과 테이블 + 주 1회 수동 재학습**으로 시작합니다. 자동화는 재학습 주기가 병목이 되는 시점에.

**방어 기제로서의 루프**

사기 수법이 바뀌면 **상담사와 모델의 불일치율이 먼저 오릅니다.** 성능 지표는 정답이 확정된 뒤에야 계산되므로 항상 늦습니다. 불일치율을 선행 지표로 삼으면 드리프트를 더 빨리 감지할 수 있습니다. 플라이휠은 성능을 올리는 장치인 동시에 **성능 저하를 조기에 알리는 센서**입니다.

### 통합-4. 실패 시나리오 — 가장 가능성 높은 원인과 사전 방지책

**가장 가능성 높은 원인: 조직 내 공감대 부족**

기술적 실현 가능성은 높고(유사 연구 풍부, 사내 데이터 보유), 배포 역량도 직전 과정에서 확인했습니다. 진짜 문제는 **"위험도 몇 점부터 조치할 것인가"에 합의가 나지 않는 것**입니다.

사기대응팀은 재현율을 원하고, 판매자 지원팀은 오탐을 싫어하고, 법무팀은 자동 조치의 근거를 묻습니다. **임계값 숫자 하나가 부서 간 이해충돌의 지점**이 되고, 모델이 다 완성된 뒤에 이 협상이 시작되면 프로젝트가 거기서 멈춥니다.

**두 번째 가능성: 작은 문제 해결**

룰로 이미 걸리는 명백한 사기만 다시 잘 맞히고, 정작 피해액이 큰 지능적 사기는 못 잡는 경우입니다. **ML 지표는 좋아 보이는데 피해액은 안 줄어듭니다.**

**기획 단계에서의 방지책**

1. **성공 지표를 ML 지표가 아니라 사업 지표로 먼저 합의한다.**
   "AUC 0.9"가 아니라 "분기 사기 피해액 20% 감소". 그러면 작은 문제만 푸는 상황을 지표가 스스로 잡아냅니다.

2. **임계값 결정을 기획 단계 안건으로 올린다.**
   모델을 다 만들고 협상하면 늦습니다. 각 부서가 FP/FN 비용을 숫자로 제출하게 하고, 그것으로 임계값 산식을 **미리** 합의합니다.

3. **실패 사례부터 본다.**
   최근 피해액 상위 100건을 먼저 분석하고, **그 유형을 못 잡으면 프로젝트 실패로 정의**합니다. 범위가 저절로 올바른 곳을 향합니다.

4. **작은 데모를 일찍 돌린다.**
   상담사 5명에게 2주간 써보게 하고 반응을 받습니다. **조직 합의는 문서가 아니라 경험에서 나옵니다.**

### 통합-5. 6개월 뒤 예상되는 기술적 부채

**가장 위협적: 외부 세계의 불안정성 — 적대적 드리프트**

일반적인 데이터 드리프트는 계절성이나 트렌드처럼 **수동적**입니다. 그런데 사기 탐지는 상대가 **우리 모델을 회피하도록 능동적으로 적응**합니다. 배포하는 순간 상대의 최적화가 시작되고, **우리가 잘 막을수록 상대는 더 빨리 변합니다.** 6개월이면 초기 학습 데이터의 상당 부분이 이미 낡아 있을 것입니다.

**두 번째: CACE**

룰과 모델이 공존하는 하이브리드 구조라, **룰 하나를 수정하면 모델에 들어오는 입력 분포가 바뀝니다.** "룰 팀"과 "모델 팀"이 나뉘어 있으면 서로의 변경이 상대의 성능을 조용히 망가뜨리고, 6개월이면 이 상호작용이 얽혀 원인 추적이 어려워집니다.

**세 번째: 레이블 오염의 누적 — 가장 조용하고 가장 위험함**

모델이 저위험으로 분류한 건은 상담사가 보지 않습니다. 검증되지 않은 그 데이터를 다시 음성으로 학습하면 **모델이 자기 실수를 강화합니다(피드백 루프 편향).** 6개월간 조용히 축적되는데, **지표상으로는 오히려 좋아 보입니다.** 모델이 놓친 것은 정답에도 없으니까요.

**대비책**

- **저위험 구간에서도 무작위 표본을 강제로 검토 큐에 섞는다.** 지금은 상담사 시간 낭비처럼 보이지만, 6개월 뒤 피드백 루프 편향을 잡아낼 수 있는 유일한 장치입니다.
- **시간 기준 평가셋을 유지하고, 최근 30일 데이터에서의 성능을 별도 지표로 본다.** 전체 기간 평균은 드리프트를 가립니다.
- **룰 변경과 모델 배포를 같은 변경 로그에 기록한다.** CACE의 원인 추적은 결국 "언제 무엇이 바뀌었는가"의 기록에 달려 있습니다.

## 마무리

Day 1에서 코드는 한 줄도 쓰지 않았지만, 직전 과정에서 붓꽃 모델을 GCP에 배포하며 막연히 느꼈던 "이제 뭘 해야 하지"라는 질문이 **구조화된 체크리스트**로 정리되었습니다.

가장 크게 남은 것은 **아키타입 선택이 단순한 분류가 아니라 예산 결정이라는 점**입니다. Human-in-the-loop을 고르는 순간 요구 정확도가 내려가고, 요구 정확도가 내려가면 비용이 자릿수 단위로 줄어듭니다. 모델을 잘 만들어서 문제를 푸는 것이 아니라, **제품 설계를 바꿔서 풀어야 할 문제를 쉽게 만드는 것** — 이것이 Day 1에서 가장 실무적인 교훈이었습니다.
